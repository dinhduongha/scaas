Sizes are stripped release bytes on a copy of the artifact: `llvm-strip --strip-all` for a cdylib or wasm, `--strip-debug` for a staticlib.

```

export QMAKE=<qt>/gcc_64/bin/qmake6 LD_LIBRARY_PATH=<qt>/gcc_64/lib     # the ua-qt row only
```

What these figures do not cover:

- **aarch64-ios is not measured.** There is no Xcode or iPhoneOS SDK on this host, so MD-12's iOS column stays open until a macOS run adds
  its cells (`sizes.py measure` picks the target up when `xcrun` exists; that path has never run). The baseline names this under `not_measured`.
- **wasm32 has no Falcon** (no libc for the vendored C, spec §12), so those cells are not the same code as the native ones.
- **CTR-PQZ-18's module budget** (≤ 1.0 MB gzip for `pqz_bg.wasm`) cannot be read from this table: that module does not exist yet, and
  `pqz-ffi-wasm` here has no prover.

MD-12's `wallet` cell is the `--no-default-features` row, because `ua-c` always has the wallet. T0 recorded "no NDK on this host"; the NDK is
installed, outside `PATH`.

### The check

- **Rule:** a cell fails on growth past 1 %, on a cell missing from the baseline, on a failed build, or when nothing was measured.
- **Deviation from MD-12's plain text:** MD-12 fails on any growth. The 1 % exists because another host's C compiler and checkout path
  (panic locations) move the bytes without any change of code. Growth inside it is printed, and the baseline moves only by hand, so it cannot
  accumulate. The owner may ask for exact comparison, at the price of a baseline per host and checkout path.
- **Positive control:** `selftest`, 11 cases through the exit code, rc 0, including this baseline with one cell +2 % (rc 1) and +1.1 % on a
  synthetic baseline (rc 1).
- **Mutants of `sizes.py`, 8 of 8 killed by `selftest`:** no growth failure; no unknown-cell failure; tolerance 3 %; tolerance 0; exit code
  always 0; a failed build ignored; a skipped row fails; nothing measured passes.
- **Against the real builds:** `check` on the full measurement, rc 0. A second build of `ua-c/default` on x86-64 gave the same bytes for both
  artifacts.

## Reference timing on this machine: pending

**Pending: run only when the machine is idle** (owner 2026-11-07: this machine may be used, alone, not beside parallel jobs). The owner's word
that it is idle starts it. It is a desktop reference, native code on a desktop CPU: it does not show that CTR-PQZ-18's phone or browser budgets
are met.

The bench is [`clients/ua-rs/examples/ua_bench.rs`](../examples/ua_bench.rs): release build, default features (`n2304-kmax4096`), no test
feature, through ua-rs's public API. It prints the machine, load, commit, profile and set on its first line, then one JSON line per item:

| Item | What runs |
|---|---|
| `pqz_r_tx_prove_pqzl`, `pqz_r_tx_prove_pqzh` | `proveTransfer` with the auditor (`R_TX`) over the release words path. The last proof of each system is checked after its item: an `R_TX` statement, valid through pqz-ffi's precompile |
| `scrypt_n17_open_vault` | `Wallet::open_vault` of a seed vault at `N = 2^17` (scrypt, then the BIP-39 seed and the arena) |
| `falcon1024_keygen_per_handle`, `slhdsa128s_keygen_per_handle` | `Wallet::ua_key` of kinds `0x0135`, `0x0133` at a new index each run |

The exact command, from the repository root:

```
cd clients/ua-rs
SCAAS_BENCH_COMMIT="$(git rev-parse --short=12 HEAD)$(git diff --quiet HEAD -- . ../zether-prover ../scaas-ct ../../pqz-core || echo -dirty)" \
  ../../scripts/capped cargo build --release --locked -j2 --example ua_bench
../../scripts/capped target/release/examples/ua_bench 21 21 | tee target/ua_bench.jsonl
```

Expected length: about one minute for the 21 / 21 run, plus the build (a relink if `target/release` is current, some minutes if not). The estimate
comes from one `ua_bench 1 1` pass on the busy machine, run only to see the bench work. Its time figures were discarded and are not quoted.
That pass's `scrypt_n17_open_vault` added 128.0 MiB of heap, which is `128 · r · N` for `r = 8`, `N = 2^17`: memory does not depend on load, so
this is the counting allocator's control.

`heap_peak_mib` counts Rust allocations only: stacks and C allocations (the vendored Falcon) are outside it, so the keygen items read near
zero added heap whatever their stack use. `vm_hwm_mib` is the kernel's high-water mark for the whole process since its start, so it reads for the
first item only.
