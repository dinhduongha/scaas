## Q1 — Falcon keys from the seed

`noble_keys.mjs` runs clientkeys' own `pqSeed` / `PQ_KINDS[kind].alg.keygen` (noble 0.7.1 `falcon512padded` /
`falcon1024padded`) and checks the `pq_kat.json` public key; 16 more seeds are `SHAKE256("scaas.ua-rs-sign.t0.q1." ‖ i, 48)`.
`falcon_seeded.c` links PQClean's sources from `pqcrypto-falcon` 0.4.1 (the crate `ua-rs` already pins) with a `randombytes`
that returns the seed once (it aborts on any other draw), so `crypto_sign_keypair` runs exactly as shipped:
`randombytes(seed, 48)`, `shake256_init/inject/flip`, `keygen`. Variants `falcon-{512,1024}/{clean,avx2}` and
`falcon-padded-{512,1024}/clean`. noble's `NTRU` class seeds `shake256.create().update(seed)` and reads 16 bytes per Gaussian
sample, as PQClean's `mkgauss` reads two `u64`s: the key pairs agree.

| Kind | Seeds | Variants | pk equal | sk equal | Negative control |
|---|---|---|---|---|---|
| `fndsa512` | `pq_kat` + 16 | 512 clean, avx2, padded clean | 51 / 51 | 51 / 51 | differs |
| `fndsa1024` | `pq_kat` + 16 | 1024 clean, avx2, padded clean | 51 / 51 | 51 / 51 | differs |

Consequence (MD-8): T3b vendors PQClean's seeded keygen; the Falcon rows of the vectors stay as they are; clientkeys needs no
PQClean code. The `aarch64` (NEON) variant was not run (no aarch64 host); T3b's vectors cover the target's build.
