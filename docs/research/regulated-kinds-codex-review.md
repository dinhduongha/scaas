# Regulated kinds: security design review

Reviewed on 2026-11-05, branch `ua-mtx-merge`, HEAD `6d7187b7`. What this change does: it adds six regulated implementations, contract-held control powers and a separate receiver-policy registry. Confidential controls act on public names and public balances without changing the proofs.

This is a source-and-document review of `docs/superpowers/specs/2026-11-05-regulated-kinds.md`, including the accepted Q1–Q8 recommendations. The regulated implementation does not yet exist. Findings about proposed mechanisms identify requirements the design must resolve, not demonstrated exploits in deployed code. No builds, tests, calibration, source edits or commits were performed. Only this report was written. Cryptographic components remain **UNAUDITED**.

1. **medium — Frozen fee recipients remain reachable through fee paths outside `_regShape`.**

   **Spec section:** §2.2, §3.2, §7; CTR-AS-05 and CTR-AS-08.

   **Problem:** `_regMove` intentionally checks only the sender's freeze and the receiver's eligibility: frozen accounts may receive ordinary credits. Consequently it cannot enforce the separate prohibition on receiving fees. `_regShape` enforces that prohibition only for envelope fees. For example, an unfrozen payer can call `payWithFee` with a frozen, eligible `feeRecipient`: its `_transfer` passes the proposed ledger hook. `payWithFeeToUA` has the same path. In `mtxPayReceiverFee`, the signed transfer has fee NONE, then a separate `_uaMove` pays the co-signed receiver fee; that recipient is also never passed to `_regShape`. `mtxWrapOrder` mints its fee directly to `msg.sender`, with the same omission. These are public fees, not the accepted confidential decoy-fee exception.

   **Concrete fix:** Add an empty base fee-recipient hook, overridden to check `F` and `R`, and invoke it with the actual resolved recipient and nonzero fee on these separate paths before effects. Keep ordinary receiver credits freeze-neutral. Explicitly decide whether DEX relayer payouts are covered too: they are currently ordinary token transfers, so the token cannot identify their fee semantics; a covered DEX payout needs its own contract-enforced check. Add these paths to the spec's path and mutant tables.

   **Evidence:** `smartcontracts/evm/src/metatx/MetaTokenBase.sol:274–293` (`mtxPayReceiverFee`), `:333–360` (direct fee payments); `smartcontracts/evm/src/metatx/WrappedToken.sol:188–197` (wrap-order fee mint); `smartcontracts/evm/src/dex/SCaaSDex.sol:513–524` (relayer share); spec `:83–87`, `:196–205`; CTR-AS-05, CTR-AS-08. The latter already expressly requires `payWithFee` coverage.

2. **high — Reusing pending grants needs operation and proposer binding that the current record does not enforce.**

   **Spec section:** §3.6, Q4.

   **Problem:** The design reuses `pending[bit][account]` for grants, revokes, renounces, disables and expiring grant edits, but does not define distinct commitments for those actions. The existing helper distinguishes only whole grants (`termsHash == 0`) and grant terms. Reusing that encoding for argument-free relaxation permits a mature grant proposal to confirm a revoke, or the reverse, without notice of the action actually executed. In addition, `_due` never compares `p.proposer` to the caller: its existing owner-generation check is sufficient only because the current callers are owner-only. Adding holder/grantor proposal paths invalidates that assumption. At one `(bit, holder)`, the owner and holder could otherwise confirm one another's proposals, contrary to the accepted same-proposer rule.

   **Concrete fix:** Commit an action tag, bit, affected account and exact action arguments into the pending hash; use a defined account key for feature disables. On confirmation require both the matching action commitment and `p.proposer == caller`, while retaining owner-generation invalidation and the confirmation window. Specify replacement/cancellation across different actions. No separate queue is needed. Include grant→revoke, revoke→grant, owner→holder and holder→owner mismatch cases in the design's tests.

   **Evidence:** spec `:247–252`; `smartcontracts/evm/src/governance/GovernanceLib.sol:46–53`, `:131–137`, `:218–238`; `smartcontracts/evm/src/governance/GovernanceBase.sol:96–114`; CTR-GOV-04, CTR-GOV-09. This is a missing binding in the proposed extension, not a claim that the existing owner-only grant flow is vulnerable.

3. **high — Clearing the controls mirror on a disable proposal bypasses the relaxation delay.**

   **Spec section:** §2.2 hot-slot mirror and §3.6.

   **Problem:** §2.2 says `disableFeature` clears the controls mirror “in the same call”; §3.6 changes that call into propose/confirm for bits 5–7. The existing style is a void library call followed by unconditional token-side effects. If the regulated override follows that pattern, the first `disableFeature(FREEZE)` proposal clears the hot bit even though governance still shows FREEZE enabled. Every frozen account can immediately spend. PAUSE has the same failure mode. Since hooks intentionally do not read `features`, the governance value cannot save them. The spec must distinguish a successful proposal from a completed disable.

   **Concrete fix:** Make delayed `GovernanceLib.disableFeature` report whether it applied the change, or synchronize the mirror from the resulting feature bit after the call. Clear the mirror only on completion. Pin that a proposal, cancellation, failed confirmation and expired proposal leave hook behavior unchanged, for both FREEZE and PAUSE.

   **Evidence:** spec `:109–113`, `:190–192`, `:247–252`; `smartcontracts/evm/src/governance/GovernanceLib.sol:313–319` (currently void, immediate); `smartcontracts/evm/src/metatx/WrappedToken.sol:265–267` (existing call-then-side-effect pattern); CTR-GOV-09. This is a design interaction to resolve before implementation.

4. **medium — An arbitrary registry can consume the relayer's proof-sized gas budget before refusing.**

   **Spec section:** §2.2, §4 preamble, §5, §8 I10, §11 risk 6.

   **Problem:** Creation accepts any registry address with code; it does not authenticate the implementation. A normal Solidity `view` interface call uses STATICCALL, which prevents writes but does not bound execution gas. A pinned malicious/proxy registry can consume nearly all forwarded gas, recurse through views, revert with large return data, or return malformed data. Placing this call before the PQZ proof does not make the refusal cheap: the outer transaction still has the proof-sized gas allowance. Unlockable feature disablement helps token recovery, but does not limit gas lost by the transaction; locked flags deliberately have no recovery. The ~8k estimate and I10's <200k refusal claim are therefore not guaranteed by this design.

   **Concrete fix:** Define a bounded registry STATICCALL with a fixed-size output buffer, strict boolean/length validation and a named failure; never convert failure to eligibility. Specify a gas-starvation check and a call budget that fits I10, with a fixed number of registry checks per path. State that an over-budget registry is treated as unavailable. Preserve the disclosed lock/disable policy; do not add a registry replacement power.

   **Evidence:** spec `:110–111`, `:132`, `:256–259`, `:301–325`, §8 I10, §11 risk 6. The repository already uses bounded fixed-output STATICCALLs at `smartcontracts/evm/src/common/SigCheck.sol:70–81` and `smartcontracts/evm/src/dex/SCaaSDex.sol:898–904`. No cap was measured or calibrated in this review.

5. **medium — The pause exception names outer selectors, but settlement sees inner selectors.**

   **Spec section:** §2.2 `_regShape`, §3.2 shape row, accepted Q6.

   **Problem:** The hook is placed in `_uaSettle`/address `_settle` and receives a selector, while the path table exempts `mtxUnwrap`, `mtxUnwrapLeg` and `mtxUnwrapToUA`. At those seats the call data names `unwrap(uint256,address,uint256)`, `unwrap(address,uint256,address,uint256)` or `unwrapToUA(address,uint256,bytes32,uint256)`. Matching the listed outer selectors blocks every sponsored unwrap during a pause. Generic `mtxExecute` and the address alias have no outer named unwrap selector at all. Q6 also accepts fee-zero holder burn, but the operative shape table still lists only unwrap exceptions.

   **Concrete fix:** Define the pause-open set in terms of the exact inner operation selectors, shared by named and generic paths, including `burn(uint256)` per Q6. Base the exception on the computed fee being zero. Explicitly exclude confidential unshield-unwrap selectors, which must remain paused. Put this corrected rule in the path table rather than leaving it in the answered questions alone.

   **Evidence:** spec `:84`, `:196`, Q6; `smartcontracts/evm/src/metatx/WrappedToken.sol:165–180`; `smartcontracts/evm/src/metatx/NormalToken.sol:64–67`; `smartcontracts/evm/src/metatx/UAMetaTxBase.sol:146–175`; `smartcontracts/evm/src/metatx/MetaTxBase.sol:187–192`; CTR-AS-06 and CTR-GOV-17.

6. **medium — The proposed Zether multi-transfer hook seat has no sender argument.**

   **Spec section:** §4.1 transfer row; §8 I9/I10.

   **Problem:** The spec places `uaOf(t.yFrom)` checking at the top of `_multi`, leaving `ZetherLib` unchanged. Current `_multi` receives only `beneficiary` and `mode`; the sender and proof are deliberately decoded from the original call data inside the delegatecalled library. The first library result is returned after transfer verification and settlement. Thus the suggested seat cannot check the sender as written. Moving the check to where the result is available violates the cheap-prefix rule; accidentally substituting the envelope subject violates U4 and fails to freeze the actual proof sender.

   **Concrete fix:** Check `_regSender(unwrap(ZetherLib.uaOf(t.yFrom)))` and the public beneficiary in each direct multi-transfer entry before it calls `_multi`, or pass the computed sender into `_multi`. Both BUNDLE and COMPACT direct entries must be covered; their signed forms self-call these bodies. Keep the leg loop unchanged and do not decode a recipient to solve this. The single-transfer entry already has `t` available before its library call.

   **Evidence:** spec `:267`, `:272–273`; `smartcontracts/evm/src/zether/ZetherLayer.sol:168–182`, `:188–206`, `:304–311`; `smartcontracts/evm/src/zether/ZetherLib.sol:614–622`; CTR-GOV-17. PQZ differs: its `_single` and `_multi` already receive the full transfer args (`smartcontracts/evm/src/pqz/PqzLayer.sol:274–293`).

7. **low — Ordered nonce cancellation bypasses the public-kind shape restrictions.**

   **Spec section:** §2.2, §3.2, §8 I4.

   **Problem:** `mtxCancelNonce` runs `preNamedUA` and bumps a lane directly. It never enters `_uaSettle`, address `_settle` or `_uaExecuteTransfer`. On kinds 8/9, a frozen subject or any subject during PAUSE can therefore submit fee-zero cancellation despite the stated shape policy. A nonzero fee eventually reaches `_uaMove` and is refused, but that does not cover zero-fee cancellation. The spec lists no cancellation exception. This changes authorization availability, although it does not move frozen funds.

   **Concrete fix:** Invoke the empty `_regShape` hook on the successful prefix of token `mtxCancelNonce` before the cancellation effect, with the real computed fee/recipient and cancellation selector. Keep router behavior unchanged through its empty override. Alternatively, an explicit rule amendment is required if cancellation is intended to stay open; do not claim the current blanket shape rule covers it.

   **Evidence:** `smartcontracts/evm/src/metatx/UAMetaTxBase.sol:93–104`; spec `:84`, `:196–197`, §8 I4; CTR-AS-05, CTR-AS-06. Confidential fee-zero submission exceptions remain governed by U4; this finding concerns public kinds 8/9.

**Verdict:** Resolve findings 1–7 in the implementation spec, especially pending-action binding and mirror synchronization. None requires changing a confidential proof, adding a governance power, or reopening the accepted Q1–Q8 choices.

**What was checked and found sound**

- **Authority and roles:** The intended powers use `GovernanceUse.use` rather than `hasRole`; its limited path debits the holder and parent budgets. Existing contract-only validation accepts only native ids backed by real contract code and excludes derived ids and EIP-7702 designators (`governance/GovernanceBase.sol:14–20`; `governance/GovernanceLib.sol:361–369`, `:421–432`; `common/SigCheck.sol:32–46`, paths under `smartcontracts/evm/src/`). Adding symmetric FORCE/RECORD conflict checks on init, grants and leaves as specified preserves the stated role separation. Distinct holder ids cannot prove distinct human controllers or multisig independence; the documents correctly avoid that promise.
- **Router signatures and replay:** The proposed flat `UA<Op>` fields include the target and operation arguments. Reusing the existing router `_ua` flow binds the target into the digest, checks the signature and shared subject/lane nonce, and rolls back the nonce on a target revert. The router domain includes chain id, router address and chain UID. `subject()` exposes authority only to the live target; another contract cannot query that subject and borrow it. Generic router execution is refused. Fee NONE supports sponsored controls; a frozen transaction submitter is not the role holder merely because it pays gas (`governance/GovernanceRouter.sol:14–18`; `governance/GovernanceRouterBase.sol:93–96`, `:158–178`, `:193–233`; `metatx/MtxPipelineLib.sol:164–195`, `:319–357`). Canonicalization of unbound relayer/fee-recipient fields must remain shared, as the spec explicitly requires.
- **Ledger coverage:** Hooking both `_update` after ticket-subject resolution and `_uaMove` covers ERC-20 transfer/allowance paths, native↔derived and derived↔derived transfers, typed transfers and batches, payments, mints, burns, public unwrap debits and DEX pulls. `_uaMove` bypasses the ERC-20 override today, so its separate hook is necessary. Generic self-calls carry an authenticated, single-use subject ticket and revert on an unguarded target (`metatx/ERC20MetaTx.sol:110–115`, `:195–205`, `:250–300`; `metatx/MetaTxBase.sol:187–198`, `:261–292`). Mandate payments call the token as the wallet, so the wallet's native balance is checked; freezing the human owner's separate id is not equivalent to freezing the wallet (`wallet/MandateWallet.sol:131–154`). Hedera mandate wallets inherit that path; native HIP-632 authorization is dispatched separately (`hedera/HederaMandateWallet.sol:6–13`; `metatx/MtxPipelineLib.sol:351–357`).
- **Confidential separation:** The intended freeze subjects are Zether's `uaOf(yFrom)` and PQZ's explicit `fromUA`, with PQZ's separate `shieldIn` payer checked before `_pullShieldIn`. Public beneficiaries and unshield recipients are valid check seats; ring recipients, shield targets and decoy-fee recipients are deliberately excluded. `_poolMove` must remain unhooked. Receiving a frozen/denied decoy credit, rollover and PQZ preparation are accepted rules, not security findings. FORCE and MODERATE use only public ledger paths; their explicit pool/self exclusions prevent reaching shield collateral. Record-bound subject, beneficiary and cumulative amount checks follow CTR-AS-04. The design does not authorize ciphertext movement or deletion and does not conflate Zether with PQZ (CTR-GOV-08/-13/-17; spec §§3.3–4.3; `zether/ZetherLayer.sol:150–219`, `:306–311`; `pqz/PqzLayer.sol:274–293`, `:323–353`, `:407–428`; `metatx/ERC20MetaTx.sol:281–300`).
- **External calls and library context:** The registry interface is view-only: STATICCALL propagates the static restriction through callbacks and cannot write token, registry or router state. That prevents a registry callback from using a control power; it does not solve finding 4. The intended `erc7201:scaas.regulated` namespace is separate from existing governance, token, UA, Zether, PQZ and wrapped storage. DELEGATECALL correctly makes `address(this)` the token clone, but preserves the router/direct caller as `msg.sender`; authority must stay `_govSubject()` as specified. There is no generated regulated slot constant or implementation to verify yet. Existing link-code-hash checks and the proposed LinkClosure extension are appropriate release checks, not proof that arbitrary initcode matches the advertised library list (`governance/GovernanceBase.sol:53–55`; `factory/OpenFactory.sol:284–317`).
- **Factory and reserves:** Factory kind checking and registration work by the enum and release, without a hardcoded six-kind ceiling. Registered regulated kinds will classify as SCaaS DEX assets. Unregistered creation refuses ids ≥2. Wrapper leg admission already refuses a registered underlying with FORCE or MODERATE, protecting wrapper reserves from the new seizure powers; outside/other-factory legs retain the documented issuer risk (`factory/OpenFactory.sol:95–113`, `:146–174`, `:309–317`; `metatx/WrappedLib.sol:122–137`; `dex/SCaaSDex.sol:260–265`; CTR-GOV-03/-16, CTR-AS-17). Factory checks attest metadata/provenance, not arbitrary code correctness.
- **Duration policy and limits:** The stated issuer-only freeze caps, pause duration/cooldown, order revocation and public-only FORCE limits agree with CTR-AS-04/05/06. Early unpause resets cooldown from the actual end; fee-zero public burn is open under accepted Q6. A freeze-backed order intentionally permits longer freezes. These are policy checks specified for future code, not experimentally verified arithmetic. Initialization must install regulated config before any initial mint, including raw library init paths: the current wrapped Zether/PQZ initializers pass fixed base-kind masks (`zether/ZetherWrappedLib.sol:35–40`; `pqz/PqzWrappedLib.sol:26–31`), so overriding token masks alone is insufficient.
- **Plain-kind cost:** Empty virtual hooks and separate regulated storage are consistent with CTR-GOV-03/-11's no-new-read requirement. No source-level argument proves generated gas or storage-access equality; the specified per-kind pins remain required. No gas claim, storage-layout pin, release size, invariant or mutant result was validated here.

All source paths in the preceding checklist are relative to `smartcontracts/evm/src/`. Cited rules checked: CTR-GOV-03/-08/-09/-11/-13/-16/-17 and their cited changes, plus CTR-AS-04/05/06/07/17; CTR-GOV-18 and CTR-AS-03/08/09/16 were read where needed to resolve exceptions. This review checked the intended contract enforcement and current call paths; it did not inspect a regulated implementation, run tests/builds, prove cryptographic soundness, or assess the parallel Fable review.
