# Codex security review: versioned PQZ keys

What this change does: it adds sequential PQZ key records to a UA and partitions confidential token state by key version. It directs credits to the current version and allows old balances to migrate by a confidential self-transfer.

Reviewed the uncommitted design on branch `ua-mtx-merge`, against the source and documents available on 2026-11-06. This is a design review, not verification of an implementation. **UNAUDITED.** No builds, tests, generators, benchmarks, deployments, or source/document edits were performed. Only this report was written. No parallel review's findings were used.

**Verdict: fix findings 1–4 before treating the statement-safety and recovery claims as established.** Keeping the version out of the proof statement is feasible, but the draft does not yet enforce all the premises it claims.

## 1. High — an existing ATTESTED signature can be redirected between duplicate-key versions

**Spec sections:** §2.1 KV-2; §3.4 KV-9; §4.2 rows 1, 2 and 5; §5 KV-12; §16 risk 6.

**Problem.** `keyOwner` excludes duplicate versions only when a proof is checked on chain. On a verifier-free registry, duplicate bytes are explicitly allowed to be stored and become current by length. `KeyReused` compares the debit key against credited keys within an operation; it does not establish that two debit accounts have different keys. A burn or refresh has no credited key to compare. The verifier's ownership check at signing time cannot invalidate an attestation after another version is stored.

Concrete sequence, without a dishonest attester:

1. A UA has version 0 with a valid stored proof and a pending TRIVIAL shield of amount B. Its per-UA debit counter is c. Obtain a valid direct burn proof, `PqzAuth`, and attestation for that account, with `p = 1`, `shieldIn = 0`, and a still-live expiry. Do not submit it.
2. Submit the UA's authorized version-1 registration with **the same key bytes**. This is allowed on the verifier-free registry; version 1 becomes current. Its separate version-bound proof need not pass an on-chain check.
3. Shield B into version 1. Its `T`, `p`, key bytes, and per-UA counter now equal those used for the outstanding version-0 burn.
4. Submit the direct burn with only `keyVersion` changed to 1. Every statement byte, the proof, `PqzAuth`, and `PqzAttest` still match. The debit updates version 1 although the signatures were obtained for version 0. The shared counter prevents a second execution; it does not prevent this first execution against the wrong account.

Likewise, an outstanding transfer to a receiver can survive that receiver's duplicate-key rotation: its statement does not change, so the credit lands in the new queue instead of failing as KV-7 promises. An attestation obtained before the duplicate exists avoids the service's duplicate rejection at issuance. This does not forge the UA or change the authorized payout, but it defeats the promised version-specific authorization and rotation boundary.

**Concrete fix.** Enforce per-UA key-byte uniqueness at **record storage**, including unproven versions and host/predecessor records. A per-UA key-hash-to-used marker can reject a second version without allowing an unrelated UA to squat someone else's global `keyOwner` claim. Retain proof-time global ownership checks and the debit/credit equality guard. This preserves O6's unchanged proof statement and `PqzAuth`; changing only the service cache does not fix outstanding signatures. Specify how version-0 replacement interacts with this marker (finding 2). Add the above issue-before-rotation/submit-after-rotation case to §14, including a burn and a receiver rotation.

**Evidence:** spec `docs/superpowers/specs/2026-11-06-pqz-key-versions.md:116–117, 130, 198–206, 215–218, 299–303, 326–330, 539–541`; `smartcontracts/evm/src/pqz/PqzCore.sol:559–606` (burn key and T), `:726–760` (counter and T), `:837–850` (authorization hashes only statement bytes), `:911–916` (header has no version); `smartcontracts/evm/src/pqz/PqzLayer.sol:330–335` (direct entry); `docs/superpowers/specs/2026-11-06-attested-verify.md:224–235, 311–321` (attestation fields, issuance-time key checks, proof-free shields).

## 2. High — retaining R-cross-set replacement can strand version-0 state in host mode

**Spec sections:** §2.1 KV-1; §2.2 KV-4; §2.3 generations; §5; §10 conflicts 3 and 11; §11 Q2.

**Problem.** The draft retains replacement of an unproven, other-set version-0 key, while also permitting ATTESTED tokens to use unproven keys. In host mode, that other-set key can already have usable proof bytes in the predecessor. Consequently, “unprovable by this registry” no longer implies “cannot have funded, spendable token state.”

Concrete supported combination:

1. A versioned gen-1 directory has no `0x0142` verifier. It holds version 0 with set-A key bytes and a valid stored set-A `R_REG` proof.
2. Gen 2 hosts that UA and enables the set-B verifier. With no host-proven version, KV-3 returns the stored version-0 key; the per-version views fall back to gen 1. An ATTESTED set-A release using gen 2 can accept it: its token checks length, and its service can read and verify the stored predecessor proof. The token release determines the attested set; 3f does not require it to equal the registry build's set.
3. Fund/use `(ua, 0)` on that token. Then submit an authorized R-cross-set replacement of version 0 with a set-B key in the host.
4. `pqzKeyAt(ua, 0)` now resolves to B, while the old token's account still contains ciphertext under A. Its key-length check fails, so the old account cannot debit or migrate. Keeping a registration pointer or the original SSTORE2 blob does not restore the token's version-0 key lookup.

For a key originally attached by `setPqzKey`, today's replacement also overwrites its active signature/proof-hash references; it does not keep all historical records available through the proposed version views. That contradicts the draft's write-once/no-deletion invariants independently of token accounting.

**Concrete fix.** Make Q2 a security prerequisite: obtain the owner ruling to retire version-0 replacement and use a new sequential version for the other set. Preserve the original version-0 bytes and views. If replacement must remain, specify an immutable identity and lookup for the old key/account and demonstrate that every affected token can still debit it; the current `(ua, version)` model has no such discriminator. Do not silently override the existing owner ruling.

**Evidence:** spec `docs/superpowers/specs/2026-11-06-pqz-key-versions.md:83–85, 132–134, 150–152, 165–169, 319–329, 491`; `smartcontracts/evm/src/ua/UARegistryLib.sol:536–547` (replacement depends on the registry's set, not token usage), `:518–520` (active key/hash/signature overwritten); `smartcontracts/evm/src/ua/UARegistry.sol:409–423` (predecessor proof/key fallback); `docs/contracts/accounts.md:1057–1077` (R-cross-set, overwritten attached keys, host behavior); `docs/superpowers/specs/2026-11-06-attested-verify.md:129–142, 307–316` (ATTESTED uses its release's set and unproven keys). Owner rule: CTR-UA-16, R-cross-set, also recorded in `docs/decisions.md:4137–4138`.

## 3. Medium — the wrong-key rejection argument is stronger than the relations guarantee

**Spec sections:** §3.6 KV-11; §4.2 rows 1, 3 and 4; §13 J1; §14 M-T5.

**Problem.** Distinct key bytes do not imply independent decryption secrets, nor must two versions have different T. Two empty accounts have identical `Trivial(0)`; two accounts holding equal TRIVIAL shields also have identical T. Thus pairing `pk_v` with another version's T need not fail the proof, even with honestly generated independent keys. A proof has no account-storage address in it: correct selection and settlement are contract obligations.

There is also an explicit valid-key counterexample to the disclosure claim. Register `pk_0 = A·s + e_0` and `pk_1 = A·s + e_1` with different small errors and the same short s. Both can have valid version-bound `R_REG` proofs, distinct hashes and distinct `keyOwner` entries. A receiver opening of a ciphertext under `pk_0` can also satisfy the relation using `pk_1`: the ciphertext decryption expression uses the **same s**, and the separate key-possession equation uses `e_1`. The requested wrong stored version need not return false. For a migration, the key difference can likewise be small rather than an independent MLWE mask. The existing normative document already distinguishes norm-valid keys from honestly generated keys and treats related-key cases separately.

This is not evidence of an overspend in a correctly implemented per-version mapping, or a break for independent fresh seeds. It invalidates the claimed cryptographic fallback for a mapping bug and the unconditional assertion that disclosure authenticates the historical version.

**Concrete fix.** Base debit safety on J1 and structural consistency: capture the selected version/key once, build T from that exact account, and settle only that account. Remove the claim that a mismatched-account bug inherently fails closed. Require M-T5 coverage with equal TRIVIAL balances and assert **which account changed**, rather than relying only on `ProofRejected`. State the honest independent key-generation assumption for migration confidentiality, preserving the existing related-key caveat. For disclosure, either define `keyVersion` as selecting a key for an amount verdict without authenticating its historical use, or require an immutable per-leg key/version commitment if the API must attest that history. Do not promise unconditional wrong-version false from the unchanged opening relation.

**Evidence:** spec `docs/superpowers/specs/2026-11-06-pqz-key-versions.md:264–275, 299–311, 513, 561`; `smartcontracts/evm/src/pqz/PqzCore.sol:743–760, 780–790` (T and zero accumulator), `:857–866` (settlement selects storage separately), `:619–639` (disclosure key selection); `docs/contracts/pq-zero-knowledge.md:511–538` (related keys and norm-only registration), `:848–855` (`R_REG`), `:958–965` (debit equations), `:1295–1302` (opening equations). CTR-PQZ-04 and CTR-PQZ-14.

## 4. Medium — sender recovery does not specify how to find all historical leg keys

**Spec sections:** §3.6 KV-11; §7.2 clients; §14 recovery checks.

**Problem.** The proposed sender procedure varies the receiver's version until the **whole** packed R matches `transferCiphertextHash`. R also contains every other recipient ciphertext and every auditor copy. For an audited single transfer whose receiver and auditor both rotated, selecting the correct receiver version while using the current auditor key never matches that hash. With op 7, every independently rotated recipient contributes another unknown version. Literal whole-bundle search becomes a Cartesian search; eight recipients with ten versions each already give 100 million combinations before the auditor's versions. Versions have no cap, and the draft gives no complete recovery algorithm or test for this case.

The necessary bytes already exist in state, so adding per-entry version storage is unnecessary for recovery. Also, a receiver cannot always find a historical credit's version in its queue after consumption: pending slots are deleted, although its entry blob survives.

**Concrete fix.** Specify independent matching against the stored blob. Recover the sender's seed version and memo/randomness, then identify each recipient version by comparing that leg's reconstructed packed ciphertext with its stored leg bytes; identify the auditor version against the stored auditor copy. Respect op 7's group randomness and auditor coefficient window. Finally reconstruct R and check its full hash. This makes candidate work additive across version lists. Give a receiver the equivalent historical-key search when its pending slot is gone. Add an audited op-7 recovery case after sender, several receivers, and auditor rotate and the recipients consume their credits. Preserve C6's no-per-entry-version-storage decision.

**Evidence:** spec `docs/superpowers/specs/2026-11-06-pqz-key-versions.md:272–275, 408–421, 543–545`; `smartcontracts/evm/src/pqz/PqzCore.sol:516–535` (R includes all legs/copies), `:644–655` (leg offsets/windows), `:681–690` (hash and readable R), `:857–864` (pending deletion); `docs/contracts/pq-zero-knowledge.md:981–984` (deterministic randomness, memo and whole-R recovery), `:1077–1082` (multi-leg bundle/memo), `:1252–1258` (state-only recovery). CTR-PQZ-19 and CTR-PQZ-23.

## What I checked and found sound

- **New-version consent and portable replay semantics.** The proposed nested typed record binds UA, uint64 version, key hash and proof hash. `_portableOk` rejects `keyData`; `_sigOk`/`_msig` supply the existing authorization rules, including sorted, accepted, minimal weighted quorums. Replaying across chains or registries is intentional portability under CTR-UA-07, not permission to substitute a key. Replaying across UAs or version numbers changes the typed digest. An observer can front-run only the exact signed registration, or compete using another genuinely authorized record. Evidence: spec §2.1; `UARegistryLib.sol:524–533, 619–654, 660–693`.
- **Membership between versions.** The immutable member identities, weights and threshold cannot change under the same UA. Acceptance can grow under CTR-UA-37; each new registration must use the accepted quorum at verification time. Replacing an operator is not removing an msig signer. An old signer/quorum is not revoked by PQZ key rotation. Evidence: CTR-UA-13; `UARegistryLib.sol:588–603, 668–693`.
- **Version-specific registration proof.** The new version is inside the 32-byte R_REG message preimage, so the same proof cannot simply be moved from v1 to v2 or another UA. Reusing the existing verifier is appropriate: it proves the supplied message, not the semantics of a particular record struct. Changing this preimage alone does not require a new relation or proofSystemId. Evidence: spec §2.1; `UAPqzVerifier.sol:49–52, 66–74`; CTR-UA-07; `pq-zero-knowledge.md:848–855`.
- **PRECOMPILE proof/authorization binding, conditional on immutable key selection.** Op 1, op 7 and burn/refresh all insert full selected key bytes and T into the statement. `PqzAuth` hashes all 640 header bytes and the complete body. The header binds chain id, token, registry, chainUid, parties, counter, p, expiry, outputs/memo context and relay binding. Distinct immutable version keys change the statement and authorization even when T happens to coincide. An old receiver/auditor-key proof then fails after a rotation, rather than crediting its old queue. Evidence: `PqzCore.sol:249–277, 452–490, 588–606, 837–850, 911–916`. This conclusion is subject to findings 1–3, not the draft's unconditional verdict.
- **Counters, entry references and old pending credits.** One counter per UA avoids cross-version `entryPtr` collisions and prevents executing a previously consumed debit again. Each account's acc/queue/floor/cleared/rollover preparation must remain independent. Credit tails under old versions remain spendable and need repeated rollover/debit processing up to the existing noise cap; rotating does not erase them. A migration settles the old debit before appending the credit to the captured current account. The totalShielded accounting equation remains valid when balances are summed over all versions. Evidence: KV-6–KV-10; `PqzCore.sol:310–339, 495–512, 748–760, 853–877`; `PqzStateLib.sol:77–100`.
- **No-version statement layout, narrowly stated.** An account selector outside the proof is acceptable when immutable unique key bytes identify its version and contract state selection/settlement is correct. No new proof statement word or new proofSystemId is inherently required by that architecture. Version-zero byte equality and proposed mutants are future checks, not results of this review.
- **Host authority and limits.** Only the first verifier-enabled generation can prove the keys; a host verifies a predecessor UA using its original signing structure. Max latest across generations and host-only proven current can support late proofs without lowering current. The implementation must reject writing a version already resolved in either generation, keep host-owned reads stable as the predecessor grows, and verify a predecessor's previously unchecked proof before marking a host version proven. A predecessor cannot see a host, so two intentionally signed records can still diverge; cross-generation/cross-chain consistency remains the stated client rule, not a contract guarantee. Evidence: spec §2.3; `UARegistryLib.sol:438–461, 489–516`; `accounts.md:1067–1075`. Finding 2 addresses the unsafe retained overwrite.
- **Anonymity and auditor limits.** One list entry per UA avoids weighting decoy selection by its number of versions, and using current for every decoy prevents explicitly choosing a recipient's obsolete version. Rotation is nevertheless public: registry events, keyVersion calldata/events, and a self-transfer identify rotation/migration timing and old-version activity. It does not unlink identities or revoke knowledge of old ciphertext, and the old seed holder can reconstruct migration randomness. The research already acknowledges the public self-transfer. On a verifier-free registry the proven `0x0142` list is empty for unproven holders: preserve 3f's service-assisted discovery/validation and do not claim the on-chain list supplies their anonymity set. Auditor copies use the auditor's current key per new operation; historical disclosure must use its historical selected key. Evidence: KV-2, KV-7, KV-11; 3f §6 lines 317–322; research §7.2 lines 611–635.
- **Node and release scope.** Named `key_version`, both-direction selector parity, version-aware keeper queues, and a nonterminal rotated-job diagnosis fit the existing model. An event since intake is evidence of a possible rotation cause, not proof that every `ProofRejected` was caused by rotation; retain the actual simulation error and do not declare an outstanding send dead. New immutable releases/reset state make the planned layout and typehash changes permissible. Zether stays separate. Evidence: spec §§6–7 and §10; CTR-UA-16, CTR-PQZ-09, CTR-MTX-29; `scaas-node/src/typed.rs`, `scaas-node/src/guard.rs`, `PqzLayer.sol:467–482`.

Not checked: executable behavior, mutants, vector equality, gas/size figures, or future 3f/3g implementation; none was built or run.
