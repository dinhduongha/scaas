## 1. Executive summary

- **There are two exploitable paths on `main` today.** Both work against any account tricked into signing a 7702
  authorization to a sweeper-style delegate `D`:
  1. **Signature path (ERC-1271 through the delegate).** `SigCheck.isValid` (SigCheck.sol:42-46) and
     `UARegistry._native` (UARegistry.sol:605-625) first try ECDSA. When the account has a designator and ECDSA fails,
     they call `isValidSignature` on the account, which runs `D`. A sweeper `D` returns the magic value for anything.
     The attacker can then sign, as the victim, every relayable action: `mtxExecute*` / `mtxTransfer` / `uaExecute*`
     (all tokens, incl. PQZ / Zether `mtxShield`), DEX orders / cancels / `mtxInvalidateNonces`, `mtxWrap`,
     `MandateWallet` owner and delegate actions (`setMandate`, `execute`, `payUnderMandate`), UA native-id auth, and
     `msig` native-member votes. This is a full drain without the key.
  2. **`msg.sender` path (code runs as the EOA).** `D` runs whenever anyone calls the victim. It can call
     `token.transfer`, `payWithFee`, `transferToUA`, `unwrap(…, attacker)`, `mtxShield`, `cancelNonce`, the owner and
     role functions (`transferOwnership`, `mint`), `MandateWallet.onlyOwner` functions, or `SmartKeyAccount.initiateRecovery`
     when the victim is a guardian. In every case `msg.sender` is the victim. Only `approve` / `transferFrom` are
     already closed (`CallerNotContract`, ERC20MetaTx.sol:273-287).
- **The fix is small and has one choke point per path.**
  - (a) `SigCheck.isValid`: a designator gets ECDSA by its base key only and never ERC-1271. This is one line, and it
    **saves** gas and bytes.
  - (b) The same change in `UARegistry._native`. `ua8`'s new `_nativePortable` already does this; `ua8`'s `_native`
    does not yet.
  - (c) Refuse a designator `msg.sender` in `MetaTxBase._msgSender()` (MetaTxBase.sol:265-271). Every token,
    `MandateWallet` and `SmartKeyAccount` reads the direct caller only through this function. Cost: about 100–120 gas
    per call, a few dozen bytes.
  - (d) Use `_msgSender()` for the four raw-`msg.sender` authority checks: `SmartKeyAccount.initiateRecovery`
    guardian :163, `SCaaSDex._onlyAdmin` :193, `OpenFactory` registrar :65, and the relayer binding
    `MtxPipelineLib._checkEnvelope` :138 (the owner chooses, D3).
  - (e) `MtxRelayFee._shape` :98: replace `target.code.length == 0` with `!SigCheck.isContract(target)`. This is a
    standalone bug: a designator that points at a code-less address passes, the call succeeds empty, and the payer
    pays for nothing.
- **The node mirrors need two small changes.**
  - DEX venue `valid_sig` (venue.rs:392-417): a designator gets ECDSA only.
  - `guard.rs:667` `chain.has_code`: should use `is_contract` semantics, so a designator payer no longer reserves the
    ≈ 0.5 M ERC-1271 gas floor (it over-quotes priced relay fees).
  - Gateway §3.3 becomes "a designator `from` whose signature does not recover is `BAD_SIGNATURE`". Simulation would
    refuse it anyway once the contracts change.
- **Chain level: already decided while this audit ran.** `/home/dockers/mba-chain-nethermind/genesis.json` had
  `"eip7702TransitionTimestamp": 0` (Prague / 7702 active since genesis) at the start of the audit. At 11:17 another
  session removed it. The README now records the owner decision: 7702 off on 7622 and on the future mainnet 22776, in
  effect at the next reset (fs3 Task 13). A throwaway node confirmed that type-4 txs are rejected
  ([eip7702-node-check-2026-10-30.md](eip7702-node-check-2026-10-30.md)). The repo has no 22776 chainspec yet. Customer chains (Ethereum
  and most L2s since Pectra, BSC, …) keep 7702, so contract-level enforcement is still required. The contracts and
  docs must keep one rule everywhere (memory "all chains same infra").
- **Clients.** Nothing signs 7702 authorization tuples. One sharp edge remains: clientkeys `signDigest(key, digest)`
  (seed.js:146) signs any 32 bytes with the native secp256k1 key. A compromised portal page could pass it the hash of a
  7702 authorization (`keccak256(0x05 ‖ rlp([chainId, addr, nonce]))`) and get exactly the phished signature. Proposed
  fix: sign only digests that clientkeys computes itself from checked EIP-712 data.
- **Non-EVM analogues exist** on Algorand (rekey to a LogicSig / app, delegated LogicSig), Aptos (account
  abstraction / signer-capability offer), Cosmos (authz to a contract), TON (W5 extensions / v4 plugins), NEAR
  (DeployContract / AddKey on the user's own account) and Hedera (ContractID keys; HIP-1340). Most cannot be detected
  by our contracts. The one place SCaaS *knowingly accepts* code authority today is Algorand: a rekeyed-to-LogicSig
  address runs `add_key_native` under the LogicSig (test `test_rekeyed_address_signs_through_account_record`).
  Decision point D6.
- **Tests that flip** are listed in §7: SigCheck.t.sol ×2, UARegistry.t.sol T-AUTH-3, UALedger.t.sol
  `test_7702_nativeFrom`, UAReceiverFee.t.sol 7702 payee, 4 parity rows + fixture regeneration, Tier1 error selector,
  node venue test, and `ua8` UARegistry tests.

## 2. How the two attacks run (for the record)

Setup: the victim V signs a 7702 authorization (any chain id, or chain id 0 = every chain) to D. The victim's code
becomes `0xef0100 ‖ D`.

- **A1, the signature path:** the attacker builds `MetaTransfer{from: V, to: attacker, value: balance}` and signs it
  with any key. Then `SigCheck.isValid(V, …)` runs: code length 23 → `isContract(V)` is false → ECDSA fails →
  `_erc1271(V, …)` staticcalls V → D's `isValidSignature` returns `0x1626ba7e` → accepted. The relayer submits it,
  with fee 0 allowed.
- **A2, the `msg.sender` path:** the attacker calls V (any calldata). D runs in V's context and calls
  `SCaaSToken.transfer(attacker, balanceOf(V))`. `_msgSender()` returns V, so the transfer goes through.

A key-only rule (ECDSA for designators) closes A1. A designator-`msg.sender` refusal closes A2. Neither weakens the
base key: V can still sign with its key, and can clear the delegation with a type-4 tx authorising `address(0)`.

## 6. Proposed minimal enforcement design

### 6.1 One helper (SigCheck)

```solidity
/// The 23-byte EIP-7702 delegation designator `0xef0100 ‖ address` (EIP-3541: no deployed code starts with 0xef).
function isDesignator(address a) internal view returns (bool) {
    if (a.code.length != 23) return false;
    bytes memory c = a.code;
    return c[0] == 0xef && c[1] == 0x01 && c[2] == 0x00;
}
function isContract(address a) internal view returns (bool) {
    return a.code.length != 0 && !isDesignator(a);
}
function isValid(address signer, bytes32 digest, bytes memory sig, uint256 cap1271) internal view returns (bool) {
    if (!isContract(signer)) return _ecdsa(signer, digest, sig);   // EOA or designator: the key really signs
    return _erc1271(signer, digest, sig, cap1271);
}
```

### 6.3 Alternatives where the owner must choose

- **D1, a designator's own key signature.**
  - (a) Key-only: ECDSA by the base key is accepted, the delegate never is. Recommended. It matches "it must really
    sign", matches `ua8` `_nativePortable`, and keeps 7702 users fully usable through relayed meta-transactions.
  - (b) Refuse every signature from a designator (frozen in SCaaS until it clears its delegation). This adds nothing
    against the sweeper, which does not hold the key. It only costs usability.
- **D2, scope of the `msg.sender` refusal.**
  - (a) Everywhere a caller's identity is authority: E3 + E4. Recommended; it is the only option that closes A2.
    Cost: a 7702 user cannot call SCaaS tokens directly while delegated. They use relayed `mtx*` (fee may be 0) or
    clear the delegation.
  - (b) Signature paths only (E1 / E2). This leaves A2 open: the sweeper still calls `transfer`. It **does not meet
    the goal**.
  - (c) Allow a designator caller only when `msg.sender == tx.origin`, meaning V's key signed this very transaction (a
    sweeper can never make `tx.origin == V`). This keeps direct calls for smart-EOA users at +2 gas, but V's delegate
    code may still run in V's own self-call batch. That conflicts with the literal "an EOA must not run code".
- **D3, relayer / submitter roles (M7 / M8).** (a) Guard only the relayer-binding check (`MtxPipelineLib:138`), which
  is the one "who may act" check. (b) Leave all of them: open roles, and only the relayer's own fee is exposed.
  Recommendation: (a) for the binding, leave the open submitters.
- **D4, calls *into* a designator.** Required: T1 (bug). Choose for T2 (wallet `execute`), T3 (native unwrap
  recipient), T4 (DEX interaction): refuse designators (literal rule, ≈ +100 gas each, cannot pay a 7702 user in
  native coin through these paths) or leave them (each is an explicit choice by the asset owner or the solver, with
  no SCaaS authority involved). Recommendation: T3 refuse, T2 / T4 leave.
- **D5, chain level.** Already decided by the owner (README-chainspec 2026-10-30): 7702 off on 7622 at the next reset
  and on 22776. Remaining questions:
  - Should the `OpenFactory`-style config checks (UnderlyingLib:111, OpenFactory:213/307, UARegistry:145/159, the
    Zether / PQZ env checks) switch to `isContract` anyway? Cheap, deployer-gated, and they matter on customer chains.
  - Keep the forge / anvil 7702 tests as the proof of the contract rule: the SCaaS testnet can no longer exercise 7702
    end-to-end after the reset.
- **D6, non-EVM analogues (§8).**
  - (a) Record them as residual risks plus wallet guidance (recommended: most are undetectable on chain).
  - (b) Algorand: refuse `Txn.sender` whose `AcctAuthAddr ≠ zero` on the Sender-authorised key ops (`add_key_native`
    and friends). This would reverse today's tested behaviour, where a rekeyed-to-LogicSig address adds its own key.

## 8. Non-EVM families (only real analogues of "a key-holder account whose authority can be handed to code")

- **Algorand: yes.** Rekey to a LogicSig or an app address, and delegated LogicSigs (the key signs a TEAL program, and
  anyone submits txns satisfying it). Phishing either is the Algorand sweeper. Detectable only for rekey
  (`AcctParamsGet AcctAuthAddr`); a delegated LogicSig is invisible to apps. SCaaS signature ops verify against the
  current auth address. Sender-authorised `add_key_native` deliberately accepts a LogicSig authority (test
  `algorand/tests/test_account.py:662`), and `probe.py:64` documents an account rekeyed to an app. → D6.
- **Aptos: yes.** Account abstraction (AIP-104 dispatchable authentication functions) and
  `offer_signer_capability`. Both hand a user account's authority to Move code. Whether a contract can query it
  (`using_dispatchable_authenticator`) is **[unverified]**.
- **Cosmos: yes.** `authz` `MsgGrant` to any grantee, including a CosmWasm contract, which then `MsgExec`s as the
  granter; the wasm contract sees `info.sender = granter` and cannot tell. `feegrant` only pays fees: not an analogue.
- **TON: yes.** W5 wallet extensions and v4 plugins send arbitrary messages from the wallet; the jetton wallet sees
  the owner wallet as sender and cannot tell.
- **NEAR: yes, at key level.** `DeployContract` / `AddKey` (full access) on the user's own account, also inside a
  NEP-366 `DelegateAction`. The code then acts with `predecessor = account`. No synchronous on-chain check; the node
  has `has_code` (near.rs:1644).
- **Hedera: yes.** An account key can be a ContractID / delegatable ContractID key, which hands HTS authority to code.
  HIP-1340 brings 7702 itself to Hedera (status **[unverified]**). SCaaS EVM tokens on Hedera get E1 / E3 like any EVM
  chain. HIP-632 `isAuthorizedRaw` needs a raw ED25519 / ECDSA key, so it is key-only already.
- **Solana: no.** A program can never make a keypair account a signer. `SystemProgram::Assign` hands over the account
  data, not signing authority; SCaaS balances are PDAs.
- **Sui: no** known analogue (address = hash of a key scheme; zkLogin / multisig are key schemes).
- **Soroban: no.** G-accounts add only key / hash / pre-auth-tx signers. C-accounts are contracts already (the
  1271-style `__check_auth`).

## 9. Clients and wallet guidance

- **Findings.**
  - No client signs EIP-7702 authorization tuples or type-4 transactions. Searched `clients/**`, `scaas-node/src`
    (no `authorization_list` / `SignedAuthorization`); the node builds plain `TransactionRequest`s.
  - The only ECDSA signer is clientkeys `seed.js:146` `signDigest(key, digest)`. It signs any 32 bytes with the native
    secp256k1 key and is exported to integrators (`seed-signer.js`; docs `clients/app.md:376`,
    `signers-clientkeys.md:661/774`).
  - UA keys sign only `ua_msg` (`signUA`), so they cannot produce a 7702 authorization.
  - P-256 passkeys cannot produce one either (wrong curve).
- **Proposed fix (E7):** `signTyped(key, td)` computes `hashTypedData(td)` internally and is the only exported EVM
  signing call. `signDigest` becomes internal, or is renamed `unsafeSignDigest` and documented "only digests this
  library computed".
- **Wallet guidance** (signers-clientkeys.md, new short rule):
  - Never sign an EIP-7702 authorization (magic `0x05`) or a type-4 transaction.
  - Never anything with chain id 0.
  - Never sign a raw 32-byte digest whose preimage the wallet did not build and show.
  - If the user's address has code `0xef0100…`, warn and offer "clear delegation": a type-4 tx authorising
    `address(0)` on the current chain id. That is the single allowed authorization, built by the wallet itself.
  - SCaaS refuses delegated callers (E3), so balances are safe but frozen for direct calls until the delegation is
    cleared; relayed key-signed `mtx*` still work.
- **Node signer:** threat-model 12 §(signer item 1) already requires refusing type `0x04` payloads; keep it.
