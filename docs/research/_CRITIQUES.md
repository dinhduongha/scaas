### contradiction-1 [contradiction] 03 (§3.5.4, §3.6, §3.9.2) vs 05 (§5.1.1, §5.2, §5.4.3, §5.8.2), 06 (§06.2.6, §06.3.4, §06.9), 09 (§09.9), 10 (§10.4.7, §10.7)

**Problem:** §03 deleted the Zether epoch model entirely, replacing it with `accSeq` (owner-signed rollOver, `epoch_blocks` = "không dùng"), and §04.10 explicitly removed `targetEpoch` from the struct. Four downstream sections still build on epochs: §05 puts `zether.target_epoch` in the intent envelope and a `target_epoch` field on `blockchain.metatx`, and derives the 3,456 tx/day/address ceiling from a 25 s epoch; §06 defines `zether_target_epoch` + `zether_epoch_deadline_block`, an `epoch_expired` job state, and a cancel-instead-of-speedup policy keyed on epoch expiry; §09.9 computes ~185 s Zether latency as "25 s epoch + 160 s"; §10.4.7 makes `epoch_number` a **required** field on `blockchain.zether.entry` and §10.7 schedules `_cron_zether_rollover`. Only §15 caught this. Implementers will build epoch plumbing that the protocol no longer has, and a required NOT NULL column with no source value.

**Fix:** Delete `target_epoch` from the §05 envelope + `blockchain.metatx`; delete `zether_target_epoch`/`zether_epoch_deadline_block`/`epoch_expired` from §06 and replace the epoch-deadline cancel rule with the §05.4.3 single-flight + `accSeq` staleness check; recompute §05.4.3 and §09.9 throughput/latency from `accSeq` (17,280/day/address per §3.5.2, no epoch wait); replace §10.4.7 `epoch_number` with `acc_seq` + `pending_seq` (not required); and rewrite §10.7's `_cron_zether_rollover` as a relayer-driven rollOver that carries an owner Schnorr signature — Odoo never holds `x` (§3.9.5).

### contradiction-2 [contradiction] 04 (§04.4, §04.6, §04.6.2, §04.6.7) vs 06 (§06.6 executeOne, §06.12.3), 08 (§08.4c), 16 (§16.0.1, P03 DoD)

**Problem:** Two mutually exclusive forwarder semantics are both stated as locked. §04.6.2 requires `require(m.amount == 0 || mode & MODE_REQUIRE_SUCCESS)` — every money flow must bubble the revert, so on inner failure the whole tx reverts, the nonce is NOT consumed and the fee is NOT paid. §08.4c mandates the opposite as a hard requirement on §04 ("fee được thu BẤT KỂ ok ... KHÔNG revert"), §06.6(c) writes `_consumeNonce` + `_collectFee` before the inner call and says the relay pool "không thể an toàn nếu thiếu", and §16.0.1/P03 DoD adopt §06/§08 ("fee **luôn** được thu kể cả khi inner call revert"). §06.12.3 then re-opens the same question §04.6.7 already closed. These produce different Solidity, a different `blockchain.metatx` state machine, and a different answer to "did the user pay for nothing?".

**Fix:** Pick one and propagate. Recommended: keep §04's mode-driven rule (bubble for `amount > 0`, swallow+charge otherwise) because it is the only one that preserves "broadcast is not payment" for principal transfers; then rewrite §08.4c and §06.6(c) as applying only to `amount == 0` logic-only meta-txs, delete §06.12.3 question 3 as already decided, and change P03's DoD line to "fee is charged on inner-revert only when MODE_REQUIRE_SUCCESS is off".

### contradiction-3 [contradiction] 10 (§10.4.5 `_check_mode`) vs 04 (§04.4), 05 (§5.3.3, §5.4.4c, §5.12)

**Problem:** §10.4.5 ships `models.Constraint('CHECK (mode_flags BETWEEN 0 AND 3)')` with the comment `0x00/0x01/0x02/0x03`. §04.4 requires `MODE_REQUIRE_SUCCESS = 0x04` on every value-carrying meta-tx and defines `MODE_KNOWN_MASK = 0x1F` (0x08 metered fee, 0x10 append-sender). The DB CHECK therefore rejects the INSERT of every legitimate money-flow meta-tx. Separately, the bit map itself is not agreed: §04 reserves 0x10 for `MODE_APPEND_SENDER` and 0x20 for commit-reveal, while §5.4.4c reserves 0x10 for commit-reveal and §5.12 asks §04 to set the mask to 0x0F.

**Fix:** Change §10.4.5 to `CHECK (mode_flags >= 0 AND mode_flags <= 2147483647)` plus an application-level check against the contract's `MODE_KNOWN_MASK` (per §04.12 item 2, bit 31 permanently unused). Declare §04.4's allocation table the single source of truth in one place, delete the 0x10 claim from §5.4.4c and the stale 0x0F row from §5.12.
