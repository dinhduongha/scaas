# Meta-transactions

Every SCaaS token is gasless: the subject (the holder of the balance) signs an intent, anyone may submit it, and
the submitter pays the gas. This file specifies the EVM meta-transaction layer that all EVM and Hedera tokens share
— v1 (`ERC20MetaTx`, `MetaToken`), v2 (`MetaTxCore`, `MetaTokenBase`, the three token tiers) — and the parts of the
v3 (Universal Account ledger) path that reuse it. Other families implement the same model natively
([networks/README.md](../networks/README.md)). Status: v1 and v2 **BUILT** (`smartcontracts/evm/src/metatx/`);
receiver-pays **SPECIFIED**.

## Native mixin, no forwarder

<a id="CTR-MTX-16"></a>**CTR-MTX-16** — Meta-transaction logic is embedded in every token (`ERC20MetaTx`), not in a
forwarder. The subject signs EIP-712 typed data whose `verifyingContract` **is the token**. There is no ERC-2771
trusted forwarder (no `_msgSender()` suffix, no 63/64 gas rule, no return bomb, no target allowlist, no swallow
mode), and no ERC-4337 bundler/paymaster dependency for token operations. A contract that does not support gasless
operation is wrapped into a meta-tx token (tier 2, [token-wrappers.md](token-wrappers.md)); a generic forwarder is
never added. Because the operation runs inside the very contract that verifies the signature, the contract checks
everything **before** it collects the fee and the operation cannot fail afterwards: **fee collected ⇔ operation
completed**, with no `try/catch` and no mode switch. Smart-contract wallets (ERC-1271; `AuthScheme 7` in the built Zether registry) are first-class signers.

<a id="CTR-MTX-14"></a>**CTR-MTX-14** — Signatures are EIP-712 typed data, never `personal_sign`: wallets display the
fields instead of 32 opaque bytes. The pinned typehash below is the only payment-intent type; there is no raw
`ecrecover` helper (it would not stop `s` malleability) — EOAs are verified with OpenZeppelin `ECDSA.tryRecover`
(65 bytes, low-s).

## `MetaTransaction` and the pinned typehash

<a id="CTR-MTX-15"></a>**CTR-MTX-15** — The struct is `MetaTxLib.MetaTransaction` (`smartcontracts/evm/src/common/MetaTxLib.sol`
is normative; a struct argument also keeps EIP-712 hashing clear of Solidity's "Stack too deep" limit). The fee is paid in **this** token (no `feeToken` field: another token lies outside this contract and
this contract holds no allowance of it); there is no `innerGasLimit` (it only means something for a forwarder that
swallows failures); `to`/`value`/`data` stay explicit (no opaque `op` + `args`); `mode` stays and is split into two
nibbles.

```solidity
struct MetaTransaction {
    address from;          // signer; balance affected
    address to;            // recipient / op target on this token (never a contract to call)
    uint256 value;         // amount (0 for pure logic ops)
    bytes   data;          // op: empty = transfer; pay(bytes32); trade(...); approve(...); unwrap(...); Zether ops
    uint256 batch;         // nonce dimension 1: the subject lane
    uint256 nonce;         // nonce dimension 2: sequence inside the lane
    uint256 validUntil;    // unix seconds
    uint32  mode;          // constraint flags + fee mode
    address relayer;       // bound relayer when MODE_RESTRICT_RELAYER
    uint256 fee;           // ppm (PERCENT) | absolute units (FIXED) | 0 (NONE)
    address feeRecipient;  // bound fee recipient when MODE_RESTRICT_FEE_RECIPIENT
}

bytes32 constant METATX_TYPEHASH = keccak256(
  "MetaTransaction(address from,address to,uint256 value,bytes data,uint256 batch,uint256 nonce,"
  "uint256 validUntil,uint32 mode,address relayer,uint256 fee,address feeRecipient)");

hashStruct(m) = keccak256(abi.encode(METATX_TYPEHASH, m.from, m.to, m.value, keccak256(m.data), m.batch, m.nonce,
                                     m.validUntil, m.mode, canonRelayer, m.fee, canonFeeRecipient))
digest        = keccak256(0x1901 ‖ domainSeparator(name, "1", chainId, token) ‖ hashStruct(m))
```

`data` is always hashed (`keccak256(m.data)`) — encoding dynamic bytes directly would break injectivity. The
typehash is pinned by `test_metaTxTypehashIsPinned`.

<a id="digest"></a>**One rule, four places.** `MetaTxLib.hashStruct` (Solidity) is the reference. Three copies must
match it byte for byte: the client library's EIP-712 builder (the reference ERP client keeps it in
`lib/eip712.py`), `scaas-node` (an alloy `sol!` struct) and the typed-data JSON handed to the wallet (the wallet
hashes it itself). Canonical zeroing (`relayer`/`feeRecipient` = 0 when their flag is off) applies in all of them.
They are locked by one known-answer vector, `smartcontracts/evm/test/vectors/metatx_kat.json`, generated by forge
(`vm.writeJson`): domain, struct, `structHash`, digest and the signature of key `0xA11CE`. The contract, node and
client tests read the same file; changing the typehash turns three tests red.

<a id="CTR-MTX-02"></a>**CTR-MTX-02** — The EIP-712 domain of a clone is the implementation's name and version plus
`verifyingContract` = the clone. OpenZeppelin `EIP712` keeps `name`/`version` as immutables, so every v1 clone has
domain `name = "SCaaS MetaToken"`, `version = "1"`, `chainId`, `verifyingContract = clone`; v2 clones use
`("SCaaS MetaToken", "2", chainId, clone)`. There is no cross-token replay because `verifyingContract` differs.
Clients read the domain through `eip712Domain()` (ERC-5267) and store `domain_name`/`domain_version` per token (`domain_name/version`).
The cost: wallets show "SCaaS MetaToken" rather than the token's own name (they read `name()` for that).

## `mode`: constraint flags and fee mode

```
bit  31 ........................ 8 | 7  6  5  4 | 3  2  1  0
     reserved (must be 0)           | FEE MODE   | FLAGS
```

| Name | Value | Kind | Meaning |
|---|---|---|---|
| `MODE_OPEN` | `0x00` | — | No constraints, no fee |
| `MODE_RESTRICT_RELAYER` | `0x01` | flag | Only `msg.sender == m.relayer` may execute |
| `MODE_RESTRICT_FEE_RECIPIENT` | `0x02` | flag | The fee must go to `m.feeRecipient` |
| bits 2–3 | `0x04`, `0x08` | flags | Reserved, must be 0 |
| `MODE_FEE_NONE` | `0x00` | enum (bits 4–7) | No fee |
| `MODE_FEE_PERCENT` | `0x10` | enum | `fee` in ppm of `value` |
| `MODE_FEE_FIXED` | `0x20` | enum | `fee` in token units |
| `MODE_FLAGS_MASK` / `MODE_FEE_MASK` / `MODE_KNOWN_MASK` | `0x0F` / `0xF0` / `0xF3` | masks | `supportedModes()` returns `0xF3` |

The low nibble holds independent **flags** (`mode & FLAG`); the high nibble holds an **enumerated** fee mode
(mutually exclusive, mask + shift). `mode & MODE_FEE_PERCENT` is a bug (a future value `0x30` would contain bit
`0x10`); use `feeModeOf(mode)` (values 0/1/2, otherwise `ModeFeeInvalid`). `validateMode` checks both unknown flag
bits (`ModeUnknownBits`, surfaced as `MetaTxUnknownMode`) and fee values above 2: accepting `0x30` today would freeze
its meaning through signatures already issued. `FeeMode` stays the canonical type of `FeePolicy`; only the separate
struct field was dropped. `mode` is part of the hash, so a bitmask creates no cross-mode replay.

**Canonical zeroing:** when `MODE_RESTRICT_RELAYER` is off, `relayer` is hashed as `address(0)`; when
`MODE_RESTRICT_FEE_RECIPIENT` is off, `feeRecipient` is hashed as `address(0)` (`MetaTxLib.canon`). The struct keeps
both fields (removing them would change the typehash). The rule is identical in contract, node and client libraries.

**Submitter normalization.** Unbound fields are not signed, yet `ERC20MetaTx` pays a non-zero `m.feeRecipient`, so
every submitter rewrites unbound fields before it builds the outer transaction: unbound
`feeRecipient := chains.fee_recipient` (the operator's cold wallet) or `0` (then the fee goes to `msg.sender`, the
lane); unbound `relayer := 0`. Wire values of unbound fields are never submitted; the `intent_id` is unchanged
([NODE-LANE-10](../node/submit-lanes.md#NODE-LANE-10)).

## Operations

Two branches serve token operations:

| Branch | Entry | Use | Status |
|---|---|---|---|
| Generic | `executeMetaTransaction(m, signature)` with an op in `m.data` | Every subject-signed token operation; composable ops | **BUILT** |
| Payment op | `data = pay(bytes32 entryRef)` (exactly 36 bytes, `to ≠ 0`) through the generic path | Invoice/order payment with a reconciliation reference; emits `PaymentSettled(from, to, amount, feeAmount, feeRecipient, entryRef)` | **BUILT** |
| Direct payment | `payWithFee(to, amount, feeMode, fee, feeRecipient, entryRef)` — `msg.sender` pays gas; fee charged on top | Contract wallets (`MandateWallet`), self-submitted payments | **BUILT** |
| Named entry points (v2) | `mtxTransfer`, `mtxTransferWithFee`, `executeMetaTransactionWithFee`, `mtxPay(…, payId, …)`, `mtxUnwrap`, `mtxUnwrapWithFee` — build the same struct, same digest | Typed ABI for wallets/explorers; on-chain pay lane | **BUILT** (`mtxUnwrapWithFee` is decoded in the token's `fallback`, ABI `IMetaTokenV2UnwrapWithFee`) |
| Batch (v2) | `mtxBatch(MetaTransaction[], bytes[])`, atomic | Saves the 21 000 intrinsic gas per item after the first | **BUILT**; node batching **SPECIFIED** |
| Zether ops | `OP_ZTRANSFER`, `OP_ZBURN` inside the envelope ([zether.md](zether.md#envelope-binding)) | Confidential transfer/burn | **BUILT** (dev chains) |

<a id="CTR-MTX-01"></a>**CTR-MTX-01** — A payment is the `pay(bytes32 entryRef)` op (`data = pay(bytes32)`) run through
`executeMetaTransaction` (v2 also through `mtxPay`): `data` is a **selector-tagged op**, never a second typehash. One
pinned struct means one type that wallets display. The ops of `MetaToken` (`_checkOp` at step 6 must check
everything; `_executeOp` at step 8 must not fail):

| `data` | Length | Checked at step 6 | Executed at step 8 |
|---|---|---|---|
| empty | 0 | balance (already) | `transfer(from → to, value)` |
| `pay(bytes32 entryRef)` | 36 | `to ≠ 0` (`to != 0`, `PayToZero`); `data.length < 4` ⇒ `MetaTxUnknownOp(0)`, never a panic | transfer + `emit PaymentSettled(from, to, value, feeAmount, feeRecipient, entryRef)` with the real fee |
| `trade(address counterToken, uint256 minCounterValue, address counterparty)` | 100 | `MODE_RESTRICT_RELAYER` set (`mode & MODE_RESTRICT_RELAYER != 0`) **and** `to == msg.sender` (`TradeLegNotRestricted`) | transfer `from → msg.sender` (the settlement contract) |
| `approve(address spender, uint256 amount)` | 68 | `value == 0`, `to == spender`, spender is a contract (`ApproveCarriesValue`, `ApproveSpenderMismatch`, `SpenderNotContract`) | set allowance |
| `unwrap(address underlying, address recipient, uint256 minOut)` (v2 wrapper tiers) | 100 | leg known, `to == recipient ∉ {0, token}`, `minOut ≤ out ≤ reserve`, `out > 0` | burn `⌈out·q⌉`, debit reserve, then transfer `out` of the underlying (exact amount); only this transfer may revert after step 7, and it reverts the whole tx |
| other | — | `MetaTxUnknownOp(bytes4)`; `< 4` bytes ⇒ `MetaTxUnknownOp(0)` | — |

`MetaToken` constants: `OP_PAY = bytes4(keccak256("pay(bytes32)"))`, `OP_TRADE =
bytes4(keccak256("trade(address,uint256,address)"))`, `OP_APPROVE = bytes4(keccak256("approve(address,uint256)"))`;
v2 wrapper tiers add `OP_UNWRAP = bytes4(keccak256("unwrap(address,address,uint256)"))` (`MetaTxUnknownOp` on
`NoUnderlyingToken`). So that `PaymentSettled` carries the real fee, the internal `_executeOp` receives
`(feeAmount, feeRecipient)` — an internal signature change, no ABI or digest change. The relayer decodes
`MetaTxUnknownOp` from the `MetaToken` ABI.

<a id="CTR-MTX-12"></a>**CTR-MTX-12** — **Gasless unwrap.** The v2 wrapper tiers accept the op `unwrap(address
underlying, address recipient, uint256 minOut)` (100 bytes, `OP_UNWRAP`): amount = `m.value` (wrapped units offered),
`m.to == recipient`. Step 6 checks it fully (leg known, `recipient ∉ {0, address(this)}`, `0 < out ≤ reserve`,
`out ≥ minOut`); step 7 takes the fee **in wrapped units** and writes the nonce; step 8 burns `⌈out·q⌉`, debits
`reserve` (effects), then transfers the underlying with the exact-amount check (interaction, checks-effects-
interactions, under the contract-wide guard). Named entry points `mtxUnwrap` and `mtxUnwrapWithFee`; the direct
`unwrap` overloads take `minOut` too. The underlying's own transfer is the **only** thing allowed to fail after step
7; it reverts the whole transaction (fee and nonce included), so "fee collected ⇔ op completed" still holds. The
fee-never-to-the-payee rule does not apply (there is no payee). Fee-on-transfer-out underlyings stay unsupported.
Without it a holder with no native gas could exit only through a contract wallet. The node side (simulation, no
batching, the narrowed grief exemption) is [NODE-LANE-22](../node/submit-lanes.md#NODE-LANE-22).

| Step | `data = unwrap(address underlying, address recipient, uint256 minOut)`, `value = wrapped`, `to = recipient` |
|---|---|
| 6 | `len == 100`, clean address words; leg known (`UnknownUnderlying`; tier 2: the single underlying); `recipient ∉ {0, address(this)}` (`UnwrapRecipientInvalid`); `m.to == recipient` (`UnwrapRecipientMismatch`, so the wallet's "to" is who receives the underlying); `out = ⌊value·den/num⌋ > 0`; `out ≥ minOut` (`UnwrapBelowMin`); `out ≤ reserve`; balance ≥ value + fee (generic) |
| 7 | fee in wrapped units from `from` to the fee recipient; nonce written (generic) |
| 8 | `burned = ⌈out·num/den⌉ ≤ value`; `_burn(from, burned)`; `reserve −= out`; then `safeTransfer(recipient, out)` + exact-decrease check (`UnderlyingTransferMismatch`); `Unwrapped(from, u, recipient, burned, out)` |
| 9 | `MetaTransactionExecuted` (generic) |

The op works on disabled multi-underlying legs (exits stay open) and during a pending rate change (at the current
rate; `minOut` protects the signer if the intent lands after the change). The holder keeps `value − burned` (dust)
and pays the fee on `value`.

## 2D nonces and lanes

Storage `_metaNonce[from][batch]`; an intent is valid iff `m.nonce == metaNonce(from, batch)`; execution increments
it. Independent lanes remove head-of-line blocking between agents and between business flows of the same subject.

| Lane derivation | Rule | Status |
|---|---|---|
| Payment request | `batch = keccak256("scaas.pay.lane" ‖ entryRef)`, `nonce = 0` ⇒ each request is payable at most once and the client can build typed data without reading the chain; v2 `mtxPay` derives the same lane on chain (`payLane(payId)`) | **BUILT** |
| Agent × purpose | `batch = uint256(keccak256(agentId ‖ purpose))` (e.g. procurement settlement, logistics milestones, payout distribution, treasury rebalance), sequential nonce inside | **SPECIFIED** (client convention) |
| Non-EVM | `(subject, lane: bytes32) → nonce: u64` in the subject's account object/wallet/PDA | **BUILT** |

`cancelMetaNonce(batch)` (direct call by the subject) increments `metaNonce[msg.sender][batch]` and invalidates every
pending intent on that lane, including ones circulating on the mesh, without a dummy transfer; v2 emits
`MetaNonceCancelled(from, batch, newNonce)` (v1 emits no event). First use of a lane costs ≈ +17 k gas (a new
storage slot). An anti-lock test is mandatory per family: X stuck on contract 1 never blocks Y on contract 2
([networks/README.md](../networks/README.md#head-of-line)).

<a id="entryref"></a>
<a id="CTR-MTX-03"></a>**CTR-MTX-03** — **Payment references.** `entryRef` is 32 random bytes; the lane of a
payment request is `keccak256("scaas.pay.lane" ‖ entryRef)` with nonce 0. A random value is unlinkable by
construction (better than a salted hash of business data) and needs no salt management; a fixed lane per request
lets the client build typed data without reading the chain and makes each request payable at most once (under
[CTR-MTX-04](#CTR-MTX-04)). Accepted cost: the first use of the lane costs +17 k gas (measured in `MetaTxGas`).
v2 tokens derive the lane on chain ([CTR-MTX-10](#CTR-MTX-10)).

```
entryRef = 32 bytes from a CSPRNG                     # carries no information; unlinkable by construction
batch    = keccak256("scaas.pay.lane" ‖ entryRef)     # lane of this request (v2 tokens: payLane(entryRef) on chain)
nonce    = 0
```

- One `entryRef` per **payment request** (an invoice may have several requests over time; each request is payable at
  most once because its lane has nonce 0).
- Pay-once holds only if every signature a client issues on a pay lane has `validUntil ≤ t_first_issue + 30 d`.
  Re-issuing terms on the same lane later than that, or signing an op with `valid_until > now + 30 d` on a pruning
  family (TON, Aptos, Solana, Sui), gives no pay-once guarantee — issue a new request (new `entryRef`, new lane)
  instead. Wallet connectors and `clientkeys` refuse such ops.
- The client stores `entryRef` with a UNIQUE constraint on the request, together with `chain`, `token`,
  `receiving_address`, `payer_address` (locked at start), `amount_base`, `issued_valid_until`.
- Do **not** derive `entryRef` from business identifiers (`keccak256(company ‖ move ‖ amount ‖ salt)` as in older
  drafts): a random value needs no salt management and cannot be brute-forced from known invoice numbers.
- Splitting: classical Zether with `n_v = 64` removed the need to split large payments; for transparent tokens one
  payment per request. If a business case needs partial payments, issue one request (one `entryRef`) per
  instalment.

Two-way verification. **Client → chain** (before signing and at push): (1) typed data is built server-side from the
request: `to = receiving_address`, `value = amount_base`, `data = pay(entryRef)`, `batch` as above, `validUntil =
issued_valid_until` (server-chosen, e.g. now + 300 s); (2) after signing the client recomputes the digest; a 65-byte
signature must recover `payer_address` (EOA); a contract wallet (ERC-1271) is accepted unverified and judged by the
node's simulation; (3) the node recomputes the digest and simulates before broadcast. **Chain → client** (on each
finalized range): (1) filter `PaymentSettled` by `contract == request.token` **and** `to == request.receiving_address`
**and** `entry_ref == request.entryRef`; (2) `amount_settled = Σ amount` of matching events; `amount_settled ≥
amount_base` ⇒ request final; more than due ⇒ final + needs attention (refund manually); less ⇒ partial; (3)
cross-check `MetaTransactionExecuted(digest)` to mark the job final; (4) drift checks: an unmatched inbound
`Transfer` to a watched wallet ⇒ a drift record; hourly `balances` vs the ledger balance of the token's journal. A
third party paying 1 unit with someone else's `entryRef` cannot complete a request (the sum must reach the amount);
an overpayment by a stranger is just money received. The full client procedure is in
[integration.md](../integration.md#payment-references).

## Pay-once horizon

<a id="CTR-MTX-04"></a>**CTR-MTX-04** — **Pay-once is conditional and is a protocol rule.** "Each payment request is
payable at most once" holds iff (1) every signature issued on a pay lane has `validUntil ≤ t_first_issue + H`,
`H = LANE_HORIZON = 30 d`, and (2) every family that prunes lane state keeps an executed lane for ≥ `H` after the
executed op's `validUntil` ([NET-ALL-01](../networks/README.md#NET-ALL-01): TON two `LANE_TTL` generations; Aptos and
Solana `PRUNE_DELAY_S`; Sui `prune` after `valid_until + LANE_HORIZON_S`). Issuers that sign terms on a lane beyond
`H` get no pay-once guarantee; a node chain on a pruning family must have `max_valid_for_secs ≤ H`. Obligations:

| Who | Obligation | Status |
|---|---|---|
| Issuer (ERP, app) | Sign one op per pay lane, or keep every op on that lane inside `H` of the first; terms signed beyond `H` get no pay-once guarantee | reference ERP client complies (**BUILT**) |
| Every signing client (connectors, `clientkeys`, app) | Refuse to sign an op with `valid_until > now + LANE_HORIZON_S` on a pruning family ([NET-APT-24](../networks/aptos.md#NET-APT-24), [NET-SOL-25](../networks/solana.md#NET-SOL-25), [NET-SUI-12](../networks/sui.md#NET-SUI-12)) | **SPECIFIED** |
| Contract | Sui `relay_pay` refuses `valid_until > now + LANE_HORIZON_S` on chain; Solana caps `valid_until` and order `expiry` at `MAX_TTL_S = 31 d` ([NET-SOL-22](../networks/solana.md#NET-SOL-22)) | **SPECIFIED** |
| Node | Refuses `max_valid_for_secs > LANE_HORIZON` on a pruning family ([NODE-STO-01](../node/store.md#NODE-STO-01)); constants pinned equal in tests (TON `LANE_TTL`, Aptos/Solana `PRUNE_DELAY_S`, node `LANE_TTL_S`, client `LANE_HORIZON_S`) | **SPECIFIED** |

## Execution pipeline

`executeMetaTransaction` (not payable) runs under a reentrancy guard in transient storage
(`keccak256("scaas.metatx.reentrancy.v1")`; v2: `keccak256("scaas.metatx.reentrancy.v2")`, covering meta-tx, wrap,
unwrap, `addReserve`, `mtxBatch`). Cheap checks come first:

| Step | Check / action | Cost class | Error |
|---|---|---|---|
| 1 | `MODE_RESTRICT_RELAYER` ⇒ `msg.sender == m.relayer` | no SLOAD | `MetaTxUnauthorizedRelayer` |
| 2 | `block.timestamp ≤ m.validUntil` | no SLOAD | `MetaTxExpired` |
| 3 | `validateMode(m.mode)` | no SLOAD | `MetaTxUnknownMode` (v2: `ModeUnknownBits` / `ModeFeeInvalid`) |
| 4 | `m.nonce == metaNonce(from, batch)` | 1 SLOAD | `MetaTxBadNonce(expected, got)` |
| 5 | Signature over the digest (`_hashTypedDataV4(hashStruct(m))`): EOA ⇒ `ECDSA.tryRecover` (65 bytes, low-s); contract ⇒ ERC-1271 `isValidSignature` staticcall (50 000 gas; 400 000 for `SubjectAccount` clones, which verify P-256 in Solidity when no precompile, [CTR-ACC-05](accounts-mandates.md#CTR-ACC-05)) | ecrecover / call | `MetaTxBadSignature` |
| 6 | Fee computation (`feeRecipient = 0` ⇒ `msg.sender`), `FeePolicy.compute` on `m.value` + `validateRecipient`, the payee check (v2), balance ≥ value + fee, `_checkOp` | SLOADs | `MetaTxInsufficientForFee`, `FeeExceedsCap`, `FeeRecipientRequired`, `FeeRecipientIsPayee`, op errors |
| 7 | Transfer the fee (v2: and write `metaNonce = expected + 1`) | SSTORE | — |
| 8 | `_executeOp` | SSTORE | — (must not fail; v2 unwrap: only the underlying's transfer may revert, undoing the whole tx) |
| 9 | `nonce++` (v1), emit `MetaTransactionExecuted(from, relayer, batch, nonce, digest, feeRecipient, fee)` | SSTORE | — |

Invariant: **fee collected ⇔ operation completed.** No `try/catch` around the op; any failure reverts everything,
fee not charged, nonce not consumed. Because the nonce check (step 4) precedes the signature (step 5), a relayer that
loses a race pays only ~24–30 k gas. v2 writes the nonce at step 7 together with the fee, so no external call (the
unwrap op) runs while the nonce is unspent; the event stays at step 9.

<a id="gas"></a>Measured gas (Foundry `MetaTxGas.t.sol`, `evm_version = prague`, execution gas; full-transaction
`gasUsed` from receipts after deploying the same contracts on the private Nethermind reference chain, Nethermind
1.39.0, Fusaka + BPO2; 2026-08-31):

| Scenario | Execution gas | Full tx gas |
|---|---|---|
| Warm lane, `MODE_OPEN`, no fee | 35 241 | 58 702 |
| New lane (nonce 0 → 1), no fee | 52 341 | 75 802 |
| Warm, `FIXED` fee | 43 565 | 67 362 |
| Warm, `PERCENT` fee | 43 511 | 67 260 |
| Warm, `FIXED` + restricted relayer + fee recipient | 43 763 | 67 560 |
| Warm lane, recipient that never held the token | 52 341 | — |

Derived: envelope = warm meta-tx − baseline = **+15 160** execution gas (≈ 17.5 k full tx), first use of a lane

## FeePolicy

<a id="CTR-MTX-13"></a>**CTR-MTX-13** — Public fee modes are `NONE`, `PERCENT` and `FIXED`, chosen by the signer per
intent through `mode`; the percent unit is ppm (1e6), because per mille cannot express 0.05 %:

- `enum FeeMode { NONE, PERCENT, FIXED }`; `PPM_DENOMINATOR = 1 000 000`; `MAX_FEE_PPM = 10 000` (1 %) — a protocol
  constant protecting signers, not a governance parameter.
- `compute(PERCENT, amount, fee)`: `fee ≤ MAX_FEE_PPM`, result `amount × fee / 10^6`. `compute(FIXED, amount, fee)`:
  `fee ≤ amount × MAX_FEE_PPM / 10^6` (FIXED is also capped at 1 % of `value` for public tokens). Over the cap ⇒
  `FeeExceedsCap(feeAmount, cap)`. The percent is of the sender's `value`, charged on top.
- `feeRecipient` is the signer's choice in every mode — usually the value a relayer publishes — and `address(0)`
  means "pay `msg.sender`". `validateRecipient`: non-NONE needs a non-zero resolved recipient (`FeeRecipientRequired`).
- `requireConfidentialSafe`: `PERCENT` on any confidential op ⇒ `PercentFeeForbiddenOnConfidential` (a percentage
  fee would reveal the hidden amount). Confidential outer fees are `NONE` or `FIXED`, and `FIXED` there is **not**
  capped at 1 % because the amount is hidden ([CTR-ZTH-07](zether.md#CTR-ZTH-07)).
- DEX fees are separate: per-market maker/taker ppm ≤ 10 000, bounded by the order's signed `maxFeePpm`
  ([dex.md](dex.md#CTR-DEX-03)).

<a id="CTR-MTX-08"></a>**CTR-MTX-08** — **The fee never goes to the payee** (v2, **BUILT**). For the transfer and
`pay` ops and for `payWithFee`, `feeAmount != 0 && resolvedFeeRecipient == to` reverts `FeeRecipientIsPayee` at
step 6, whether the recipient was bound by the signer or defaulted to `msg.sender` (a payee self-relaying with a fee
is refused). "Payee" = `m.to` when `m.data` is empty (transfer) or is the `pay` op. For `trade` the `to` is the
settlement contract and for `approve` the value is 0 (a `FIXED` fee there already fails the 1 % cap, a `PERCENT` fee
computes to 0), so the check does not apply to them. The fee mode, amount and recipient stay the signer's choice;
the 1 % cap and "percent of the sender's amount, charged on top" are unchanged. The check costs ~100 gas; v1 lacks it.

## v2 core

<a id="CTR-MTX-07"></a>**CTR-MTX-07** — The v2 meta-tx base is `MetaTxCore`: the same `MetaTxLib` struct, typehash,
`canon` and nine-step order; domain `("SCaaS MetaToken", "2", chainId, clone)` for all three tiers; the pipeline runs
over a **memory** struct so that named functions can build one; v1 sources (`ERC20MetaTx.sol`, `MetaToken.sol`)
stay byte-identical (a v1 implementation built from changed sources would not be v1). It adds the
`MetaNonceCancelled` event. The version string tells wallets which ABI they face; replay safety stays on
`verifyingContract`.

| Item | v1 | v2 |
|---|---|---|
| Struct, `METATX_TYPEHASH`, `hashStruct`, `canon` | `MetaTxLib` | **same library, unchanged** |
| Domain | `("SCaaS MetaToken", "1", chainId, clone)` | `("SCaaS MetaToken", "2", chainId, clone)` |
| Pipeline input | `MetaTransaction calldata` | internal `_execute(MetaTransaction memory m, bytes calldata sig)`; `executeMetaTransaction` passes its calldata struct (one copy — v1 already copies it to memory inside `hashStruct`) |
| `_checkOp` / `_executeOp` | calldata slices, `abi.decode` | memory; arguments read with `mload` at fixed offsets after the length check; an address word with any of its upper 96 bits set ⇒ `MetaTxUnknownOp` (as `abi.decode` would revert), so one op has exactly one encoding and one digest |
| Reentrancy slot | `keccak256("scaas.metatx.reentrancy.v1")` | `keccak256("scaas.metatx.reentrancy.v2")` (transient; covers meta-tx, wrap, unwrap, `addReserve`, `mtxBatch`) |
| Step 6 | balance, fee, recipient non-zero, `_checkOp` | + the payee check |
| Step 8 | must not fail | must not fail, except the underlying's transfer inside the unwrap op (reverts everything) |
| Nonce write | step 9 | step 7, with the fee; the event stays at step 9 |
| `cancelMetaNonce` | no event | emits `MetaNonceCancelled(from, batch, newNonce)` |
| Allowance lockdown | `approve` spender contract, `transferFrom` caller contract | unchanged ([CTR-TOK-01](token-wrappers.md#CTR-TOK-01)) |
| ERC-1271 gas | 50 k; 400 k for `SubjectAccount` clones | unchanged (`SUBJECT_ACCOUNT_IMPL` immutable) |

Ops in `MetaTokenBase` (all tiers): the v1 table above — empty ⇒ transfer; `pay(bytes32)` (36 bytes, `to ≠ 0`) ⇒
transfer + `PaymentSettled`; `trade(address,uint256,address)` (100 bytes, restricted relayer, `to == msg.sender`);
`approve(address,uint256)` (68 bytes, `value == 0`, `to == spender`, spender a contract); unknown ⇒ `MetaTxUnknownOp`.
Wrapper tiers add `unwrap(address,address,uint256)`; on `NoUnderlyingToken` it is `MetaTxUnknownOp`.
`payWithFee(to, amount, feeMode, fee, feeRecipient, entryRef)` (direct path, `msg.sender` pays gas) is kept and gets
the payee check.

## Named functions

<a id="CTR-MTX-09"></a>**CTR-MTX-09** — The named functions `mtxTransfer`, `mtxTransferWithFee`,
`executeMetaTransactionWithFee`, `mtxPay`, `mtxUnwrap`, `mtxUnwrapWithFee` and the batch `mtxBatch` live in
`MetaTokenBase` (so every tier has them) and **only build a `MetaTransaction` and run the same pipeline**. Each
enforces a mode shape (`MtxModeShape`), nothing else. The digest of a named call equals the digest of
`executeMetaTransaction` with the same struct, so one signature works on both paths and one lane is consumed once.
They are ABI sugar; nothing breaks without them.

All are `nonReentrant`, return `bool` and call the same internal `_execute(m, sig)`. Mode bits are the `MetaTxLib`
constants:

| Function | Struct it builds | Mode shape required (else `MtxModeShape(mode)`) | Adds |
|---|---|---|---|
| `mtxTransfer(from, to, amount, batch, nonce, validUntil, mode, relayer, sig)` | `data = ""`, `fee = 0`, `feeRecipient = 0` | `mode & ~MODE_RESTRICT_RELAYER == 0` (fee `NONE`) | typed ABI |
| `mtxTransferWithFee(from, to, amount, batch, nonce, validUntil, mode, relayer, fee, feeRecipient, sig)` (short: `mtxTransferWithFee(…, mode, relayer, fee, feeRecipient, sig)`) | `data = ""` | fee nibble `PERCENT` or `FIXED`, `MODE_RESTRICT_FEE_RECIPIENT` set, `feeRecipient ≠ 0` (the sender names who is paid) | typed ABI; the payee check applies |
| `executeMetaTransactionWithFee(m, sig)` | `m` as given (any op) | fee nibble ≠ `NONE`; recipient bound **or** relayer-default ("relayer or a third party") | a selector that says "this intent pays a fee" |
| `mtxPay(from, to, amount, payId, validUntil, mode, relayer, fee, feeRecipient, sig)` | `data = OP_PAY ‖ payId`, `batch = payLane(payId)`, `nonce = 0` | any valid mode (fee optional) | on-chain lane derivation; `PaymentSettled(…, entryRef = payId)` |
| `mtxUnwrap(from, underlying, wrapped, recipient, minOut, batch, nonce, validUntil, mode, relayer, sig)` | `to = recipient`, `value = wrapped`, `data = OP_UNWRAP ‖ underlying ‖ recipient ‖ minOut`, `fee = 0`, `feeRecipient = 0` | only `MODE_RESTRICT_RELAYER` may be set | gasless exit |
| `mtxUnwrapWithFee(from, underlying, wrapped, recipient, minOut, batch, nonce, validUntil, mode, relayer, fee, feeRecipient, sig)` | as `mtxUnwrap`, fee fields from parameters | fee `PERCENT`/`FIXED`, `MODE_RESTRICT_FEE_RECIPIENT` set, `feeRecipient ≠ 0` | fee paid in wrapped units before the burn |
| `mtxBatch(MetaTransaction[] ms, bytes[] sigs)` | each `ms[i]` as given | as `executeMetaTransaction` per item | atomic; one outer tx for many items |
| `payLane(bytes32 payId) view returns (uint256)` | — | — | the lane clients must use for `payId` on this token |

Exact equivalences (each is a test):

```
mtxTransfer(f,t,a,b,n,v,mode,r,s)              ≡ executeMetaTransaction({f,t,a,"",b,n,v,mode,r,0,0}, s)
mtxTransferWithFee(f,t,a,b,n,v,mode,r,x,R,s)   ≡ executeMetaTransaction({f,t,a,"",b,n,v,mode,r,x,R}, s)
executeMetaTransactionWithFee(m,s)             ≡ executeMetaTransaction(m,s)            (plus the shape check)
mtxPay(f,t,a,p,v,mode,r,x,R,s)                 ≡ executeMetaTransaction({f,t,a,pay(p),payLane(p),0,v,mode,r,x,R}, s)
mtxUnwrap(f,u,w,t,o,b,n,v,mode,r,s)            ≡ executeMetaTransaction({f,t,w,unwrap(u,t,o),b,n,v,mode,r,0,0}, s)
mtxUnwrapWithFee(f,u,w,t,o,b,n,v,mode,r,x,R,s) ≡ executeMetaTransaction({f,t,w,unwrap(u,t,o),b,n,v,mode,r,x,R}, s)
```

So: same digest, same events (`MetaTransactionExecuted`; `PaymentSettled` for `mtxPay`), same nonce space (a
signature consumed through one path fails `MetaTxBadNonce` on the other), same KAT. A named function never accepts an
intent that the generic path would refuse, and refuses some the generic path accepts (wrong shape), never the other
way round.

`fee` is not canonicalised under fee mode `NONE` (only `relayer`/`feeRecipient` are, by `canon`): a struct signed
with fee `NONE` and a leftover `fee ≠ 0` is valid on the generic path but not through `mtxTransfer`/`mtxUnwrap`,
which put `fee = 0`. Clients MUST sign `fee = 0` and `feeRecipient = 0` for every no-fee intent.

What the names do not do: no second typehash, no `chainId` or `wrapper` field in the struct (both are met by the
EIP-712 domain: `chainId` + `verifyingContract` = the wrapper clone); no decoding of `data` to find "the amount" (the
amount is `m.value`, already the base of the percent fee); no gas promise — they hash the same 11-field struct and
save only calldata (no dynamic `data`, and for `mtxPay` no `batch`/`nonce`). An earlier estimate of a "≈ 4 k gas"
saving assumed a fast path with its own short typehash and does not apply.

<a id="CTR-MTX-10"></a>**CTR-MTX-10** — In `mtxPay(…, payId, …)`, `payId` **is** the payment reference `entryRef`
(`PaymentSettled.entryRef`), and the lane is derived **on chain**: `batch = payLane(payId) =
uint256(keccak256("scaas.pay.lane" ‖ payId))`, `nonce = 0`, so `mtxPay` pays a given `(payer, payId)` at most once
**through `mtxPay`**. The same `entryRef` can still appear in a `PaymentSettled` from `payWithFee`, from the generic
`pay` op on another lane, or after `cancelMetaNonce` on a later nonce: reconcilers match
`(payer, payee, amount, entryRef)`, book the first `PaymentSettled` for an `entryRef` and treat a later one as a
reconciliation exception, never as a second payment. A client that wants a different lane for a payment uses
`executeMetaTransaction` with the `pay` op (still valid).

`payLane(p) = uint256(keccak256(abi.encodePacked("scaas.pay.lane", p)))` (short: `payLane(p) = uint256(keccak256("scaas.pay.lane" ‖ p))`) — the same value v1 clients derive off
chain, so the lane of a payment does not depend on the token version. v1 has no `payLane`; clients call it on v2
(`eip712Domain().version == "2"`) and keep the off-chain derivation for v1 ([CTR-TOK-12](token-wrappers.md#CTR-TOK-12)); "At most once" therefore holds per path.
The node and the client store the derived lane with the job, so a pay job never changes lanes after it is signed.

<a id="CTR-MTX-11"></a>**CTR-MTX-11** — **No second typehash.** There is no `PAY_TYPEHASH` and no `batchMtxPay` with a
partial-success bitmap: one type means one wallet display. `mtxBatch` is **atomic** (all items or none) — partial
success would need a non-reverting copy of steps 1–6. One failing item costs the relayer the whole batch's gas, so
the node batches only items bound to its own lane ([NODE-LANE-11](../node/submit-lanes.md#NODE-LANE-11)): items
whose `relayer` is bound (`MODE_RESTRICT_RELAYER`) to the submitting lane, per `(chain_key, token)`, flushed at 50
items or 3 s; unwrap items are never batched. Rules: `ms.length == sigs.length` (`MtxBatchLengthMismatch`), `≥ 1`
(`MtxBatchEmpty`), no explicit cap (the block gas limit is the cap); items run in order through `_execute`;
`msg.sender` is the relayer for every item (restricted-relayer intents keep working); any item reverting reverts the
batch, so fee collected ⇔ op completed holds per item and per batch; items may mix ops and payers but never tokens or
chains (it is a function of one token). The one exception to "one typehash" is the Universal Account path, which has
its own `UAMetaTransaction` type ([CTR-UA-19](universal-account.md#CTR-UA-19)).

Measured (`test/v2/MetaTxGasV2.t.sol`, clones, warm lane): `mtxTransfer` ≈ 660 gas and `mtxPay` ≈ 140 gas below the
generic path, `mtxTransferWithFee` ≈ 200 below, `executeMetaTransactionWithFee` ≈ 85 above (dispatch + shape check);
the v2 generic path is ≈ 2.2–3.9 k below v1 on every row. `mtxBatch` saves the 21 000 intrinsic gas per item after
the first, plus warm re-reads of shared slots, minus the ABI overhead of `MetaTransaction[]`/`bytes[]` (the token
address is pre-warmed as `tx.to` anyway). `mtxUnwrapWithFee` has 13 parameters, more than the non-via-IR ABI decoder
holds: the token decodes it by hand in `fallback` (same selector, ABI and checks as the decoder: 13 head words, clean
address/`uint32` words, `bytes` in bounds; interface `IMetaTokenV2UnwrapWithFee`), and Solidity callers build its
calldata by hand. `fallback` checks the selector before the reentrancy guard (a `TSTORE` inside a `STATICCALL` would
halt).

## v1 implementation `MetaToken`

`contract MetaToken is ERC20MetaTx, IERC20Payment` (kind `META`, **BUILT**) inherits the measured `ERC20MetaTx`
mixin unchanged. One implementation serves tiers 1 and 2, chosen by `underlying`:

| | Tier 1 standalone (`underlying == 0`) | Tier 2 wrapper (`underlying != 0`) |
|---|---|---|
| Supply | `initialSupply` minted to `creator` at init; `mint(to, v)` by `minter` only (0 = fixed supply) | only through `wrap` |
| `decimals` | from `initData` | read from `IERC20Metadata(underlying).decimals()` at init |
| In / out | — | `wrap(amount)` (measures the real **balance delta** received and mints exactly that) / `unwrap(amount, recipient)` |
| Invariant | `Σ balance == totalSupply` | also `underlying.balanceOf(this) >= totalSupply` |

`initData` (fixed v1 ABI): `abi.encode(string name, string symbol, uint8 decimals, uint256 initialSupply, address
minter)`. Tier 2 uses `name`/`symbol`, ignores `decimals` (read from the underlying) and requires `initialSupply == 0
&& minter == 0` (`WrapperHasNoMint`). Clone safety:

- the implementation's `constructor(address factory_)` sets `FACTORY` and `_SELF` (immutables, correct for every
  clone) and locks the implementation (`_initialized = true` on its own storage);
- `initialize(creator, underlying, verifier, version, initData)` — `require(msg.sender == FACTORY)`, once,
  `verifier == 0` (kind `META`); the factory calls it **in the same function** as `CREATE2`;
- `name()`, `symbol()`, `decimals()` are overridden to read the clone's storage;
- provenance getters `factory()`, `creator()`, `underlying()`, `verifier()` (= 0), `implementation()` (= `_SELF`),
  `version()`;
- no `pause`, blacklist, freeze, owner or upgrade: a permissionless token ([token-wrappers.md](token-wrappers.md#permissionless-vs-controlled)).

## Receiver-pays

<a id="receiver-pays"></a>
<a id="CTR-MTX-05"></a>**CTR-MTX-05** — A new named function `mtxPayReceiverFee(m, payerSig, fee, feeRecipient,
rfValidUntil, payeeSig)` in v2 `MetaTokenBase` carries the payee's EIP-712 co-signature `ReceiverFee(bytes32
paymentDigest, uint256 fee, address feeRecipient, uint256 validUntil)` in the token's own domain, where
`paymentDigest` is the **full EIP-712 digest** of the payer's intent. The payer's `MetaTransaction` and typehash are
unchanged; the payer runs the nine-step pipeline untouched; then `fee` moves from the payee to the resolved fee
recipient in the same transaction. `paymentDigest` is consumed once by the payer's nonce, so the co-signature is
single-use with no new storage, and it is bound to one token, chain, payer, amount and `entryRef`. The "no second
typehash" rule concerns the **payment intent**; `ReceiverFee` is a different message signed by a different party (as
`MandateWallet` has its own types), so payer wallets still show one transaction type. Cost: payees sign one more
typed message.

<a id="CTR-MTX-06"></a>**CTR-MTX-06** — **Shape and availability.** The payer op is `pay(entryRef)` (36 bytes) with fee
mode `NONE` (one fee per intent), `MODE_RESTRICT_RELAYER` set, `batch = payLane(entryRef)`, `nonce = 0` (as `mtxPay`,
so "once per `(payer, entryRef)`" holds); `fee` is an absolute amount, `0 < fee ≤ m.value`; the co-signed
`feeRecipient` is non-zero (the named-fee convention) and `≠ m.to` (the payee check). The payer's `feeRecipient`
field is **not** checked (`canon` zeroes it, and the submitter may rewrite it, [NODE-LANE-10](../node/submit-lanes.md#NODE-LANE-10)).
No 1 % cap: the payee signs the exact amount it gives up and can never lose more than it receives in this call.
Events: `PaymentSettled(…, N, entryRef)` unchanged (gross), plus `ReceiverFeePaid(paymentDigest, payee, feeRecipient,
fee)`; the payer's books do not change; the payee books receipt `N` and expense `F` (net `N − F`). **Availability:**
v2 tokens of the next implementation version of each tier (EVM and Hedera children); older v2 clones and v1 lack it
(clones are immutable) — v2-only, no v1 router (owner). Not in `mtxBatch`. Jobs carrying a receiver fee travel only
on the restricted bus scope (`bus.scope = restricted`) ([NODE-MESH-17](../node/mesh.md#NODE-MESH-17)). A co-signing receiving wallet is a **hot
collection wallet**.

Messages. Payer (unchanged type): `MetaTransaction{from: payer, to: payee, value: N, data: pay(entryRef), batch:
payLane(entryRef), nonce: 0, validUntil, mode (fee NONE | MODE_RESTRICT_RELAYER), relayer: the submitting lane, fee:
0, feeRecipient: any (not checked)}` in domain `("SCaaS MetaToken", "2", chainId, token)`; `paymentDigest =
_hashTypedDataV4(hashStruct(m))`. Payee (new, same domain):

```solidity
bytes32 constant RECEIVER_FEE_TYPEHASH =
    keccak256("ReceiverFee(bytes32 paymentDigest,uint256 fee,address feeRecipient,uint256 validUntil)");
```

`feeRecipient` must be non-zero: with "0 ⇒ `msg.sender`" a mempool copier could front-run and take the fee; the
payee names the relayer's fee address (the node's `chains.fee_recipient`). No nonce: `paymentDigest` executes at most
once (payer nonce), and only through this function does the co-signature have any effect.

```solidity
event ReceiverFeePaid(bytes32 indexed paymentDigest, address indexed payee, address indexed feeRecipient, uint256 fee);
error ReceiverFeeShape();   // not pay op; payer fee mode != NONE or fee != 0; relayer unbound; lane/nonce not payLane/0; feeRecipient 0
error ReceiverFeeExpired(uint256 validUntil, uint256 nowTs);
error ReceiverFeeAmount(uint256 fee, uint256 value);        // fee == 0 or fee > value

function mtxPayReceiverFee(MetaTxLib.MetaTransaction calldata m, bytes calldata payerSig,
                           uint256 fee, address feeRecipient, uint256 rfValidUntil, bytes calldata payeeSig)
    external nonReentrant returns (bool);
function receiverFeeDigest(bytes32 paymentDigest, uint256 fee, address feeRecipient, uint256 validUntil)
    external view returns (bytes32);
```

Order:

1. Shape (`ReceiverFeeShape`): `m.data` is `pay(p)` (36 bytes), `feeModeOf(m.mode) == NONE`, `m.fee == 0`,
   `m.mode & MODE_RESTRICT_RELAYER ≠ 0`, `m.batch == payLane(p)`, `m.nonce == 0`, `feeRecipient ≠ 0`; `m.feeRecipient`
   is deliberately not checked (`canon` zeroes it; a submitter may set it). Then `block.timestamp ≤ rfValidUntil`;
   `0 < fee ≤ m.value`.
2. `feeRecipient == m.to` ⇒ `FeeRecipientIsPayee`.
3. `bytes32 d = _execute(m, payerSig)` — the unchanged nine steps (payer → payee `N`, `PaymentSettled`,
   `MetaTransactionExecuted`); `_execute` returns its digest (internal change only).
4. `_requireValidSignature(m.to, receiverFeeDigest(d, fee, feeRecipient, rfValidUntil), payeeSig)` (EOA, ERC-1271 with
   `_erc1271Gas(m.to)`, HIP-632 on Hedera children).
5. `_transfer(m.to, feeRecipient, fee)` (cannot fail: the payee just received `N ≥ fee`); emit `ReceiverFeePaid(d,
   m.to, feeRecipient, fee)`.

Equivalence: the payer side is exactly `mtxPay`/`executeMetaTransaction` with the same struct — same digest, events
and nonce. A payer signature landed through any other path makes the co-signature dead (no fee is taken).

Invariants: **RP1** the payee's net change from the call is `N − fee ≥ 0`; the payer's is `−N`; the fee recipient's
`+fee`. **RP2** A co-signature takes effect at most once and only together with the exact payer intent it names.
**RP3** No signed field can be changed by the relayer. **RP4** Fee collected ⇔ payment completed (one transaction).

| Threat | Defence |
|---|---|
| Relayer raises the fee or redirects it | `fee`, `feeRecipient` signed by the payee |
| Payee signature replayed on another payment | bound to `paymentDigest` (domain = token + chain) |
| Payer forces a fee on the payee | needs `payeeSig` |
| Race: someone lands the payer intent alone, or copies the call to take the fee | payer relayer bound (required) and `feeRecipient` non-zero (required) |
| Co-sign key compromised | it controls the receiving wallet: use a hot collection wallet with an automated sweep |
| Fee leaves the payee negative | `fee ≤ m.value` (RP1) |
| Malicious ERC-1271 payee wallet | `staticcall` with the token's gas cap; failure reverts the whole call (payer intent stays valid elsewhere) |

The co-signing key controls the receiving wallet (a `SubjectAccount` key validates any digest and authorizes
`executeAsOwner`; there is no scoped key kind), so the receiving wallet for this mode is a dedicated hot collection
wallet (EOA or `SubjectAccount`) holding only incoming receiver-pays funds, swept automatically to a cold treasury; a
cold receiving wallet cannot co-sign and must not offer this mode. A scoped key kind that validates only
`ReceiverFee` preimages with a fee cap is a planned `SubjectAccount` change ([accounts-mandates.md](accounts-mandates.md#limitations)).
Bytecode size: the 24 576-byte CI gate covers every tier and both Hedera children; if one exceeds it, the
`ReceiverFee` hashing and check move to an external library (`ReceiverFeeLib`, public functions). Node and client
touchpoints (job field `receiver_fee`, `token.features`, booking): [node/sponsorship.md](../node/sponsorship.md#receiver-pays),
[integration.md](../integration.md#inbound).

Gas (estimate): `mtxPay` + payee signature (~4 k EOA, ERC-1271 up to its cap) + `ReceiverFee` hashing (~1 k) + one
transfer (~7 k warm, ~25 k new recipient) + event (~2 k): **+14 to +32 k** over `mtxPay`. Tests: each shape error
(unbound payer relayer, wrong lane or nonce, zero `feeRecipient`); a payer intent with a non-zero unbound
`m.feeRecipient` succeeds; fee 0, fee = value, fee > value; recipient = payee; co-signature over another digest;
expired co-signature; replay after the payer intent landed through `executeMetaTransaction` (bad nonce); ERC-1271
payee (`SubjectAccount`) and Hedera HIP-632 payee; RP1/RP4 under fuzz; event fields; node accept rules and the forced
`restricted` scope. Families: EVM and Hedera v2 only; v1, Zether and non-EVM families do not have it (no fee fields
off EVM) — there the options are payee self-relay and sponsorship.

## Security

| Threat | Defence |
|---|---|
| A client prices its own payment (sends a small amount) | `value` is built from the business document server-side; the client only returns a signature |
| A third party pays 1 unit with someone else's `entryRef` | the settled sum must reach the amount; a stranger's overpayment is only money received |
| Paying twice | one pay lane with nonce 0 per request ([CTR-MTX-03](#CTR-MTX-03)) |
| A relayer front-runs and changes the recipient | `to/value/data` are in the digest; `MODE_RESTRICT_RELAYER` |
| Replay across chains or tokens | domain `chainId` + `verifyingContract` |
| Front-running `initialize()` of a clone | atomic init in the factory + `msg.sender == FACTORY` |
| Someone calls `initialize()` on the implementation | the constructor locks the implementation |
| Grief a relayer with meta-txs that surely revert | the node's simulation gate; nonce check before the signature check; expired intents dropped |
| Signature malleability | OpenZeppelin `ECDSA.tryRecover` (low-s) on chain; client verifiers refuse `s > n/2` |
| A wrapper redeems more than its reserve | the invariant `reserve >= totalSupply` (v2: the solvency invariant), fuzzed ([CTR-TOK-05](token-wrappers.md#CTR-TOK-05)) |
| Settlement contract: a leaked trade leg executed alone | the token executes `trade` only when `relayer == to == msg.sender` |
| Settlement contract: a malicious token fakes a transfer | balance deltas are measured; the seller chose `counterToken` in its signature |
| Settlement contract: a fee lands in the settlement contract | `settle` refuses a leg with a fee whose `feeRecipient ∈ {0, dex}` |
| Personal data on chain | on chain there are only wallet addresses, amounts and random `entryRef`s — no names, no order numbers |

Replay protection in short: the domain carries `chainId` + `verifyingContract`; the 2D nonce is consumed on
execution; `validUntil` bounds every intent (300 s for portal payments); `cancelMetaNonce(batch)` lets a signer
withdraw. Relayers never hold user funds: tokens grant no allowance to relayers, a meta-tx moves only the signed
`from → to`, and the DEX holds no balance between transactions. Node-side threats are in
[node/threat-model.md](../node/threat-model.md).
