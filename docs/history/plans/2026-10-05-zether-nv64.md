# Zether n_v=64 + large-balance reading; push main; resume Solana fixes

## Context
The owner reviewed the Zether limits (2026-10-05):
- `n_v = 32` caps ONE transfer at 2^32 units (Z-VND 1 unit = 1 ₫ ⇒ 4.29 tỷ ₫, large payments split, 1-bit leak).
- The wallet reads balances by BSGS only up to `DECRYPT_BOUND = 2^40` (`zether-prover/src/elgamal.rs:11-13`), ≈ 1,1 nghìn tỷ ₫; the prover needs the plaintext balance to spend (`zether-prover/src/api.rs:158,187`), so an account above that is stuck in that wallet, while the contract allows up to `MAX_TOTAL_SHIELDED = 2^54` (`ZetherToken.sol:83,137`).
- A 2^44 total cap was rejected (Z-VND ≈ $690M is too small).

Owner decisions:
1. `n_v = 64`, `n_b = 64` (ruling: relax SRS §7.3 `n_b − n_v ≥ 24`, justified because every balance ≤ total ≤ 2^54 < 2^64 − 24 bits of margin… record the exact argument).
2. Client BSGS bound 2^40 → **2^44**.
3. **Wallet-side balance cache on the device** (not on-chain, not backed up to Odoo) + a **large-account reader tool** (BSGS up to 2^54) for lost caches.
4. Disclosure bundle: **keep as is** (full 256 B per transfer, SRS §9.4).
5. Total cap stays 2^54.
6. Push `main` cec3f32 (family labels + Pi coin type) and resume the S12 Solana fixer: approved.

### C. Zether change (new branch `feat/zether-nv64` from main, one opus implementer, then independent review)
- Contracts: `ZetherVerifier.sol` `NV = 64`; `ZetherToken.sol` `VALUE_BOUND` → `1 << 64` (amount/disclosure/fee bound = `2^n_v`); statement/proof layout sizes for the 64-bit BP#1 (6 rounds); `MAX_TOTAL_SHIELDED` unchanged.
- Prover: `zether-prover/src/zether.rs` `N_V = 64` (+ `check_fee`, decode lengths). `elgamal.rs`: replace the fixed `DECRYPT_BOUND` with a **client-configurable BSGS** `Bsgs::new(table_bits, bound_bits)` — `bound_bits ≤ 54`, `table_bits` 18–27; the baby table is public data (multiples of G, no secret, any account/key), generated on the client or loaded from a cached/downloaded file and verified, regenerable at any time; steps = 2^(bound_bits − table_bits). Defaults: mobile/wasm `table_bits 22, bound_bits 44`; desktop `24–26, 54` chosen from available RAM; wasm refuses > 2 GiB. Keep the sorted 16-byte-entry array. New API `check_balance(acc, x, b)` = `[b]G == C − x·D` (cheap cache validation), `decrypt(ct, x, bsgs)` and `decrypt_pending`.
- Wallet cache (clientkeys / portal signer): store `{ua, token, accSeq, balance}` in the encrypted vault; on open validate with `check_balance`; on rollOver `b += pending` (BSGS ≤ 2^44 on pending only); on own debit `b −= v + fee`; if invalid/missing and `acc` > 2^44 ⇒ tell the user to run the reader.
- Same component in the native CLI (`zether-read-balance`, for lost caches on big accounts): `--bound-bits` (≤ 54) and `--table-bits` — **default 24** (owner: "dùng bảng 537 MB" ⇒ 2^24 entries; ≈ 256 MiB with the prover's 16-byte sorted entries, ≈ 2^30 giant steps ≈ 6 min worst case on desktop), allowed range 20–27 (27 ⇒ ≈ 2 GiB, ≈ 1 min); refuse a value that would not fit in available RAM; reads `acc` from chain RPC or a pasted ciphertext; never sends keys anywhere. Wallet table stays 2^22 (≈ 64 MiB) for the 2^44 pending bound.
- Vectors/KATs regenerated (py_ecc ≥ 8 in user space for `kat.py`), spec `2026-10-03-zether-design.md` §1/§8/§12 + rulings (n_v, n_b relaxation, DECRYPT_BOUND, cache, reader) and the gas table re-measured.
