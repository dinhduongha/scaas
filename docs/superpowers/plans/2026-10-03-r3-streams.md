  (no leading `_`, no `@api.private`), never accept company ids from clients; no field named after a type.

- Odoo: `dms_blockchain/lib/addresses.py` (canonical address per family), `lib/families.py` (register

  `{family, contract, from, op_kind, payload (hex), signature, public_key, auth_kind, digest, valid_until, extra}`),
  `blockchain.payment.request._issue_family` / `_accept_family`, ingest finalizes ops by `digest`.

What every network stream delivers (design → review → plan → TDD → review, as above):
1. **Design doc** `docs/superpowers/specs/2026-10-03-net-<family>.md`: contract-level meta-tx (R30) in the
   network's language — the exact signed payload (domain: network id + contract + lane + nonce/entryRef + expiry
   + op hash; reject cross-contract/cross-network replay), signature schemes accepted (the network's wallet
   scheme(s) + secp256r1 WebAuthn passkey where the network verifies P-256 natively (R31), + seed-wallet keys
   (R32: same payload, signed by our client)), how the relayer pays fees from its own lane accounts (native
   sponsorship only for relayer fees), how head-of-line blocking is avoided (R62), DEX model, finality,
   events, and a one-paragraph "confidential payments feasibility" note (Zether is EVM-first — R34 §5).
2. **Contracts** in `chains/<family>/` (Hedera: Solidity in `smartcontracts/src/hedera/`): token (META
   equivalent: `pay(from,to,amount,payRef)` emitting PaymentSettled-equivalent + executed event carrying the
   signed-payload digest; allowance/authorisation only to contracts — R26), mandate (as EVM `MandateWallet`
   R25: deposit, delegate signature, caps per payment/period, payees, expiry, revoke, payRef once), DEX
   (R35 on-chain settlement semantics: verify BOTH signed orders, price limits, `filled[orderHash]` no
   overfill, fee ppm per market maker/taker with on/off and 1 % cap inside the signed order max-fee, cancel by
   signed op so a cancelled order never settles; batch where the network allows; record deviations, e.g. TON
   async ⇒ escrow). Contract tests in the network's native framework, including the ANTI-LOCK test: a subject
   signs op X on contract 1 and op Y on contract 2; X is withheld; Y succeeds; then X succeeds.
3. **Adapter** `scaas-node/src/adapters/<family>.rs` implementing `ChainAdapter` for `signed_op` jobs (build
   + simulate the native tx calling the contract's relay entrypoint from the lane account, sign with the lane
   `Signer`, submit, status, committed sequence, final head, events normalized to
   `{event: "MetaTransactionExecuted"|"PaymentSettled", contract, block_number, block_hash, tx_hash, log_index,
   from, to, amount, entry_ref, digest}` with hashes as `0x`+64 hex and addresses in `addresses.canonical`
   form). Add ONE arm in `scaas-node/src/adapters/mod.rs::build`. Proptest the payload/response decoders.
   Unit tests + an e2e `scaas-node/tests/e2e_<family>.rs` (`#[ignore]`, fake Odoo harness like `tests/e2e.rs`)
   against a LOCAL devnet: two lanes from a 24-word mnemonic, a payment through `lane_step`, finality via
   `index_step`, and the anti-lock property end to end. If the devnet genuinely cannot run here, ship unit
   tests against recorded vectors and record the gap.
4. **Odoo family module** `dms_blockchain/lib/fam_<family>.py` (+ one import line in `dms_blockchain/lib/__init__.py`):
   `build_terms(request, valid_until)` builds the exact payload bytes your contract verifies (no RPC — R20;
   chain-specific static data goes in `blockchain.chain`/`blockchain.token` fields you may add in your own
   small model file `dms_blockchain/models/blockchain_<family>.py`), `verify` where Odoo can verify cheaply.
   Cross-implementation vector: the SAME payload/digest computed by Python, by the contract test and by the
   Rust adapter test. Odoo tests on your DB/port.
5. **Portal connector** `dms_blockchain_bridge/static/src/js/connectors/<family>.js` registering
   `window.dmsChainConnectors.<family> = { label, available(), async connect() -> {address, publicKey},
   async sign(terms) -> {signature, publicKey} }` (lazy-loaded only when the payer picks this network; no
   library loaded otherwise; vendored pinned libs only if unavoidable). Do NOT edit `chain_pay.js` (the lead
   wires connectors in). Node test of the connector logic with a fake wallet object.
6. Report as in the process section, plus: devnet used (image/version, ports), what ships vs seam.
