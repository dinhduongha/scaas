# Round 3 / S6 — Hedera Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans. Steps use `- [ ]`.

**Goal:** Hedera (HSCS) as a payment network: ED25519 Hedera accounts sign contract-level meta-tx (HIP-632),
relayer lanes run one tx at a time over the JSON-RPC Relay, Odoo accepts native-key payers, portal connector seam.
**Spec:** `docs/superpowers/specs/2026-10-03-net-hedera.md` (R63, R6-1..R6-5).
**Branch / DB / ports:** `r3-hedera`, `dms_test_chain_6` / 8926, anvil 31960–31969.

## Global Constraints
- Own only: `smartcontracts/src/hedera/**`, `smartcontracts/test/hedera/**`, `smartcontracts/script/hedera/**`,
  `bamboo-node/src/adapters/hedera.rs` (+1 arm in `adapters/mod.rs`), `bamboo-node/tests/{e2e_hedera.rs,vectors/hedera_*}`,
  `dms_blockchain/lib/fam_hedera.py` (+1 import), `dms_blockchain/models/blockchain_hedera.py` (+1 import),
  `dms_blockchain/tests/test_hedera.py` (+1 import), `dms_blockchain_bridge/static/src/js/connectors/hedera.js` (+ node test).
- No new dependency (Python: `cryptography` ships with Odoo; Rust: `ed25519-dalek`, `proptest` already there).
- forge 1.3.5 has no ed25519 cheatcode ⇒ forge mock of 0x16a emulates "the account's key signed these 32 bytes" with
  a 64-byte compact secp256k1 signature; real ed25519 is checked by Python + Rust on the shared KAT vector.

## Review Focus
1. A 64-byte signature can never authorise a payment for an account whose key did not sign (EIP-2098 compact ECDSA,
   unknown account, missing precompile ⇒ fail closed).
2. Odoo never marks a native-key signature as verified for the payer (key↔account binding is on-chain only).
3. Hedera never runs the pipelined EVM submitter path through this adapter (one tx in flight per lane).
