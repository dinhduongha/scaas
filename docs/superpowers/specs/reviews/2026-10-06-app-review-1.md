# Review 1 — SCaaS app design (rev 1.1, R150–R172)

Reviewer: adversarial design review, read-only. Inputs: the app spec; NI rev 3.3 §3, §7; spec D (signers
follow-ups, R250–R268); TW2 §2, §5.3; A2 §11.5, §13; asset suite §3.9, §8.1, §9.3; tender R192; code at `scaas`
`main` (`scaas-node/src/{gateway.rs,gwauth.rs,dex.rs,abi.rs,chain.rs}`, `clientkeys/src/*`,
`zether-prover/src/{wasm.rs,api.rs}`, `smartcontracts/evm/{src,script}`, `smartcontracts/ton/shim/server.ts`).
Owner rulings in the brief were not re-argued.

## Verdict: **FIX-THEN-GO**

The architecture holds up: one SPA, lazy family adapters, the client builds every byte, gateway or self-paid
submission, admin tokens kept in memory. Nothing here needs a redesign. Seven findings are rated high and must be
fixed in the spec before A0 starts:
- **H1–H3** are holes in the money path: a hostile RPC fools the signing review, the approve spender is not on an
  allowlist, and the seed sits in the same JavaScript realm as seven SDK dependency trees.
- **H4** is a cross-spec bug that makes the backup predicate wrong.
- **H5** is spec D not folded in.
- **H6–H7** are CSP and URL-guard rules that either break the app as written or do not guard what they claim to.

The rest are correctness gaps against the node and contract specs, and items to cut.

## High

### H1 — A hostile or compromised RPC defeats the signing review (§4, §5.2, §8.1 #15, §10.5, R158, R170)

**Problem.** The review is "decoded fields, token metadata from chain reads", and those reads come from the configured
RPC. Public RPCs are third parties, so `config.json` being intact does not protect anything the RPC answers.
- **`decimals` spoof.** If the RPC answers 24 instead of 18, the user types "1". `AmountInput` encodes 10^24, the
  review renders "1 TOKEN" with the same wrong decimals, and the user signs for a million tokens. The display is
  consistent with the bytes and both are wrong.
- **Allowlist bypass.** The R158 check "`isDeployedHere` on a configured factory", the "recipient kind" row and the
  "spender must be a contract" check (`eth_getCode`) all rest on answers the RPC can forge.
- **Chain identity is never checked.** The Network row shows the config label, not what the RPC says it is.
- **Settings offers a per-chain RPC override (§8.1 #15, "session only").** This contradicts R170 ("dials only URLs
  from `config.json`"). It is exactly the lever a "use this faster RPC" social-engineering attack needs. In
  node-served mode the exact `connect-src` blocks it anyway; in static mode the meta CSP (`https:`) lets it through.

**Fix.**
- **Pin token metadata in config.** `chains[].tokens[]` carries `decimals` and `symbol`. A curated token whose chain
  answer differs is refused, not shown. Non-curated tokens show the raw integer next to the decimal and need the
  explicit-add step. Refuse `decimals > 36`.
- **Check chain identity once per RPC when the adapter loads.** Refuse the chain on any mismatch:

  | Family | Check |
  |---|---|
  | EVM, Hedera | `eth_chainId` |
  | Sui | `sui_getChainIdentifier` |
  | Solana | `getGenesisHash` equals the key's `<genesis>` |
  | Soroban | `getNetwork().passphrase` equals `networkPassphrase` |
  | Aptos | ledger `chain_id` |
  | Cosmos | `status.node_info.network` |
  | TON | `masterchainInfo` / config check |

- **Check the EIP-712 domain read.** Assert that `eip712Domain()` returns `chainId` = config and
  `verifyingContract` = the token being signed for.
- **Cross-check security-critical reads.** `rpc` is already an array, so when two or more RPCs are configured, check
  decimals, code presence and factory provenance against two of them.
- **Delete the RPC override**, or keep it in dev builds only.
- State in §10 that `config.json` integrity equals host integrity. Signing it, or adding SRI to same-origin hashed
  assets, adds nothing in either mode, because `index.html` comes from the same host. The third parties to defend
  against are the RPCs and the gateways.

### H2 — "Spender must be a contract" is not an allowlist (§8.1 #8, §8.3, §10.5 Operation row)

**Problem.**
- R26 (`_isContract`) is a token-level backstop against EOA spenders. Any attacker-deployed contract is a contract.
- The review rule for `approve` and the DEX funding step ("`approve(dex)` offered if allowance is short") never says
  which contract, or how much.
- Combined with H1, a forged `isDeployedHere` or code answer gets a real curated token approved to a hostile spender.
  That is the drain path.

**Fix.**
- The spender must be one of:
  - the config `contracts.dex` of that chain, or
  - the wrapper being wrapped into, after verifying `legOf(underlying)`/`underlying()` on the wrapper and that the
    wrapper is curated or has factory provenance.
- Every other spender is refused, with no override outside dev builds.
- The amount defaults to exactly what the operation needs, never `2^256−1`, plus a "revoke" action on the token page.
- Add a review row "Spender: <name> (configured DEX | wrapper of <underlying>)".

### H3 — The seed and its derived keys share one JavaScript realm with seven SDK dependency trees (§3.1, §6.2, R166)

**Problem.**
- §6.2 keeps the decrypted seed "inside the signer object" on the main thread for up to 5 minutes idle.
- The same realm lazily loads the stellar-sdk, cosmjs, @ton/*, aptos ts-sdk, @mysten/sui and @solana/kit trees and
  all their transitive dependencies (axios, eventsource, urijs, bignumber.js, elliptic, …).
- The seed signer signs without a prompt (D R263: "The seed signs silently").
- One compromised transitive package in any chunk the user loads can therefore read the seed while it is unlocked.
  That is a permanent loss on all families, not one bad signature.
- Spec D §5.3 treats "XSS while the page is open" as unmitigated. Most of that exposure comes from the dependency
  trees, and it is cheap to shrink.

**Fix.**
- Run the vault and the seed signer in a dedicated module Worker that imports clientkeys only (no family SDK, no
  React). The worker's API is:
  - `unlock(pin | prf)`
  - `account(family, i)` returns public data only
  - `sign(family, signingInput)` takes bytes the main thread built and checked
  - `lock()`
- Seed, entropy and private keys never cross `postMessage`. The idle and hide timers live in the worker.
- A compromised main thread can still ask for signatures while the vault is unlocked, but it cannot take the phrase
  with it.
- Same pattern for Zether: the conf-vault open (`openConfKey`) happens inside the prover worker, so `x` never sits
  in the main realm either (§8.4 now passes `{x}` from the main thread).
- About 100 lines of code. It also confines the scrypt allocation (D R259 `RangeError`) to the worker.

### H4 — Adding a passkey origin counts as a backup (R165 × spec D R251/§4.2)

**Problem.**
- `SubjectKey` includes `originHash`, so `keyId` differs per origin.
- R165's flow for the second deployment mode ("add a key for that origin from the first one") therefore adds a
  **second key row with the same `(x, y)`**.
- Spec D §4.2 counts `keyCount` for EVM and Hedera, so `hasBackup` becomes true while the user holds exactly one
  credential.
- With the switch ON, the add-origin flow, which R252(c) always allows, unlocks value operations without any real
  backup. Static plus node-served is the case the owner asked for, so this will happen.

**Fix.** The D §4.2/§4.3 predicate counts **distinct credentials**: P-256 keys are de-duplicated by `(x, y)` across
`rpIdHash`/`originHash`. `keys[]` in `backupStatus` carries `x, y`. Add `backup_policy.json` rows: "same passkey,
two origins ⇒ 1 key". The accounts screen groups keys by credential: "1 passkey, 2 origins".

### H5 — Spec D is not folded in; the app and D contradict each other (§3.2, §3.3, §4, §6, §15)

D was committed after rev 1.1. Concrete conflicts:
- **Vault (§6.2).**
  - Says "encrypted vault blob in IndexedDB (scrypt + AES-GCM, optional PRF)". There is no v2 device-key layer
    (R255).
  - Missing details: DB `scaas-clientkeys`, store `kv`, key `vault:seed:<label>` (R257), `navigator.storage.persist()`
    and the shown refusal, and R258's "clearing site data = losing the device" notice before the first device-bound
    write.
  - Missing the "v2 blob without device key ⇒ phrase import only" state, the `RangeError` stop (R259), and BE/BS key
    metadata (R254) with its labels.
- **Backup switch (R250).** The switch is "`config.json` `policy.requireBackupKey` (validator §4.3 of APP)". The app
  §4.1 schema and §4.3 validator do not have it, and no screen implements D §4.1: receive and fund hidden, value
  refused, exit-only, add-backup first.
- **Connectors (R266).**
  - App §3.2 ("ported from the portal connectors") and §3.3 `signers/extension/{eip6963,wallet-standard,keplr,
    freighter,tonbridge}.ts` describe a second implementation.
  - D requires the app to import clientkeys `src/wallets/<family>.js` (with `win` injected) and `wallets/evm.js`
    (EIP-6963 + `walletKind`).
- **Envelope rules (R263).**
  - The Solana seed signer must sign OCMS kind 1 only.
  - App §6.1 `SignRequest` has `'solana-raw'` and nothing stops the seed signer's `canSign` from accepting it.
- **Two encoder interfaces.**
  - App §5.1 has `buildIntent`/`signRequest`.
  - D §7.2 has `checkTerms(terms, shown)`/`signingInput`/`packSignature` + `signFamily`.
  - Pick one: the app adapter calls D's `signingInput`/`packSignature` and runs `checkTerms` against what the review
    showed (see M7).
- **Streams.** §15 has no D edges:
  - A3 needs D1 (policy), D2 (vault v2) and D6's app part.
  - A9–A14 need D4 (seed family signers) and D5 (wallets moved).
  - A16 = D7.
  - D's own order (D1 → D3 → D2 → A0 → D4 → D5 → D6 → D7) must interleave with A0 → A1 → A2 → A3.

**Fix.** Rev 1.2 folds in all of the above. §6.2's "Uses" list adds `openStore`, `deviceKey`, `sealDevice`,
`openDevice`, `needsBinding`, `backupStatus` and `passkeyFlags`.

### H6 — The CSP in §10.1 breaks the app or leaves gaps

Each item is checked against how the named libraries behave.
- **(a) Trusted Types blocks the Worker.** `require-trusted-types-for 'script'` makes `new Worker(url)` a
  TrustedScriptURL sink in Chromium. Vite emits `new Worker(new URL("/assets/…", import.meta.url), {type:"module"})`,
  which throws, so the Zether worker (and the H3 key worker) never start.
  - **Fix:** add `trusted-types scaas-worker` and one policy whose `createScriptURL` accepts only same-origin
    `/assets/*.js`, used by the two worker constructors.
- **(b) `style-src 'self'` blocks Radix.** shadcn's Dialog/Sheet use Radix `RemoveScroll`. Its
  `react-remove-scroll-bar` injects `<style>` elements through `react-style-singleton`, and the only nonce source is
  `get-nonce` (`__webpack_nonce__`), which a static host cannot supply. The result is CSP violations on every dialog
  and broken scroll-lock compensation.
  - **Fix:** `style-src 'self'; style-src-elem 'self' 'unsafe-inline'`. Style injection is low value to an attacker
    under Trusted Types. The alternative is a patched copy, which is costlier.
- **(c) The meta CSP cannot stop framing.** The static meta CSP cannot carry `frame-ancestors` (§10.1 says so). On a
  host that ignores the generated headers (R161 "weaker meta CSP"), the review and sign buttons can be clickjacked.
  - **Fix:** at boot, `if (window.top !== window.self)` render nothing but a warning, before the router mounts.
    That is one line.
- **(d) Runtime-learned origins are not in the exact `connect-src`.** Node-served computes `connect-src` from
  `config.json` + `[api.oidc.issuers]` + `extra_connect_src`, and `npm run csp` only from `config.json`. But R170
  dials OIDC endpoints discovered at runtime (the token endpoint is often on another host, e.g. Google) and DEX home
  gateways learned from `/v1/dex/homes`. All of these are blocked, so OIDC in static mode and remote DEX homes cannot
  work under the exact headers.
  - **Fix:** see L1 (config pins OIDC origins) and L2a (no browser dialing of remote homes).
- **(e)** Playwright must fail on any `securitypolicyviolation` event. Otherwise (a) and (b) ship unseen. The
  `node-served` suite asserts header bytes, not behaviour.
- **(f) Workers in static mode.** A meta CSP does not apply to workers; a same-origin worker gets its policy from its
  own response headers. In static mode without headers the Zether worker has no CSP at all. Say so; `npm run csp`
  should emit worker headers too.

### H7 — The URL guard covers only the app's own `fetch`; SDK traffic bypasses it (§10.7, R170)

**Problem.**
- "One function used by every `fetch`" does not reach the SDKs. stellar-sdk (axios/feaxios), cosmjs, `@ton/ton`
  (axios), the aptos client and `@solana/kit` transports issue their own requests, with `redirect: "follow"`,
  default credentials, and in some cases default endpoints such as friendbot or horizon defaults.
- In static mode the meta CSP is `connect-src 'self' https: wss:`, so nothing else limits them. R170 is then
  unenforced exactly where the most third-party code runs.

**Fix.**
- Install the guard globally at boot, before any adapter chunk loads, by wrapping `globalThis.fetch`,
  `XMLHttpRequest.prototype.open` and `WebSocket`:
  - origin must be in the allowlist;
  - force `redirect: "error"` and `credentials: "omit"`;
  - refuse anything else.
- Still pass explicit transports where an SDK accepts one: viem `http(url, {fetchFn})`, `SuiHTTPTransport({fetch})`,
  `AptosConfig({client})`.
- e2e asserts zero requests to origins outside config.
- This also covers the polling-only rule: refuse `wss:` unless configured, so a WebSocket-based confirm helper
  (`@solana/kit` subscriptions) fails loudly in tests.

## Medium

### M1 — Node-served mode on the default loopback admin bind is refused by the app's own guard (§4.3, §10.7, §13.2, R160)

**Problem.**
- NI §3 requires TLS only for a non-loopback `admin_bind`, so the default operator setup is `127.0.0.1:<port>`
  reached by SSH tunnel.
- `nodes[].admin = "self"` then resolves to `http://127.0.0.1:…`, and the production guard and validator refuse
  `http:` outside dev builds.
- Passkeys cannot use an IP as `rpId`; only `localhost` works.
- Separately, `redirect_uri = <origin>/` (§9.4) breaks static hosting under a sub-path.

**Fix.**
- `"self"` may be `http:` when `location.protocol === "http:"` and the hostname is `localhost`/`127.0.0.1`/`::1`
  (a secure context), and never otherwise.
- The validator accepts `passkey.rpId = "localhost"` only there, and the app README says "tunnel to `localhost`, not
  `127.0.0.1`, if you use passkeys".
- `redirect_uri = origin + pathname`.

### M2 — There is no way to find a passkey account on a new device, after clearing site data, or on the second origin (§6.2, R165)

**Problem.**
- `creationOptions` sets a random user handle (webauthn.js, review S4-H1), and assertions do not return the public
  key.
- The account address is `CREATE2(keccak(abi.encode(firstKey incl. originHash, guardian)))`.
- With a synced passkey on a fresh browser, or the other deployment mode before the first origin has added a key,
  the app has nothing to look up. The spec covers only "add a key from the first origin", which assumes that origin's
  IndexedDB still exists.

**Fix.** Specify a "find my account" flow:
1. Take one assertion over a random challenge.
2. Recover the P-256 public key from it (two candidates).
3. Compute `keyId(x, y, rpIdHash, originHash)` for each origin the config lists.
4. Try `predictAccount` with guardian 0 / the configured guardian, then a `KeyAdded(keyId)` topic search from the
   factory's deployment block (bounded, paginated).
5. Fall back to "paste your account address", verified by `hasKey`.

After the first success, store `{credentialId, x, y, account, origin}` in the R254 key metadata.

### M3 — The gateway error contract is free text, and the app's logic depends on it (§9.1, §11, R159)

**Problem.**
- `gateway.rs` answers `{"error": "<text>"}`. Examples: `"token not served by this relayer"`, `"unknown chain"`,
  `"circuit breaker open: …"`, `"submit busy"`, `"expired"`, and `"simulation: " + decode_revert(...)`.
- `abi.rs::decode_revert` returns the Rust `Debug` form of known **v1** errors and hex only for unknown ones. So
  `errors.chain.evm.<name>` for v2 errors (`FeeRecipientIsPayee`, `UnwrapBelowMin`, `WrapPausedForRateChange`) needs
  hex while v1 errors arrive as Rust syntax.
- §9.1 then keys behaviour on the text ("a `400 token not served` reply disables the gateway path").

**Fix.**
- N1 adds `{error, code, revert_data?}` with stable codes `UNKNOWN_CHAIN`, `TOKEN_NOT_SERVED`, `BREAKER_OPEN`,
  `SUBMIT_BUSY`, `EXPIRED`, `BAD_SIGNATURE`, `SIMULATION_REVERT` (with raw `0x…` revert data) and `RPC_UNAVAILABLE`.
- The same contract applies on `/v1/dex/*` and `/v1/ops`.
- The app decodes revert data with its own ABI and maps `errors.node.<code>`.
- Delete the "`/v1/gateway` absent ⇒ assume served" fallback: N1 precedes A2 (M4), so it is dead code.

### M4 — Stream order and dependencies (§15)

- **A2's gate needs N1.** A2's gate is Playwright `evm` send/pay *via the gateway*. The gateway listens on another
  port, so the call is cross-origin and needs N1's `gateway_cors_origins`. The order is A2 → N1. Move N1 before A2.
- **A1 does not depend on A0.** The skeleton, config, CI and budget work need no encoders.
- **A0 is a seven-family port** (about 1.5 k lines, plus vector export and the wasm web build) placed in front of the
  first EVM screen. Split it, still all seven families in v1:
  - **A0-evm** (DEX/v2 helpers, `--target web` build) before A2;
  - **A0-<family>** as the first step of each A9–A14.
  - D4 depends only on the A0-<family> parts it uses.
- **N2 is far away.** A9–A14 gate on `/v1/ops`, and N2 depends on node P3, which is late in the node queue
  (TODO.md: P2 → P3 → … ). Gate A9–A14 on self-paid first, then add a second gate per family "gateway via `/v1/ops`"
  once N2 lands. Otherwise six app streams sit blocked behind the node.
- **Owner rule "finish all specs before app code".**
  - `/v1/ops` is "exact schema fixed by N2 and added to NI".
  - §17 lists NI/SCaaS corrections "listed, not made".
  - Write the `/v1/ops` request/response schema (per family `op` payload = the `signed_op` job body, `public_key`,
    `chain_key`) and make the §17 edits before A0.
- **Zether e2e has nothing to deploy with.** `script/Deploy.s.sol` deploys factory v1/v2, SubjectAccountFactory,
  MetaTxDex and OrderBookDex, but no `UniversalAccountRegistry`, verifiers or `ZetherToken`. The `zether` e2e needs a
  dev deploy script; add it to A6.
- **A15 conflicts with CI.** A15's "Vietnamese completion" contradicts the CI check "same key set in both languages"
  from A1. Each stream writes its VI strings; A15 is the review/approval pass.

### M5 — The app is the "wallet" that the asset-suite and tender specs rely on (§1.2 non-goals vs AS §3.9, §8.1, §9.3; tender R192)

**Problem.**
- AS R201/§3.9: "wallets show a blocking notice before a first receive" of a `*_REG` token (kinds 5–7 in
  `OpenFactoryV2`).
- AS §8.1: wallets show managed-market disclosures and eligibility before signing.
- AS §9.3 puts the issuer wizard, compliance console and holder pages "per the app spec".
- The app spec lists regulated tokens as a non-goal. Its catalogue reads `versionOf(token)` and would show a
  `*_REG` token as an ordinary one.
- Tender R192 adds `mtxPayReceiverFee` as a new implementation version per tier.

**Fix.**
- **Minimum for v1:**
  - decode `kind` 0–7;
  - kinds 5–7 are view-only, with the §3.9 disclosure text and no send, receive or DEX until an app stream ("AS8 app
    screens", listed as PLANNED in §15) adds the flows;
  - managed DEX markets (`dex_market.managed`) are shown "unavailable" the same way.
- **Choose named functions from a `(kind, version)` table**, falling back to generic `executeMetaTransaction` (still
  valid, TW2 R138) for unknown versions.
- **`termsHash` links:** the document URL must come from config, because §10.6 forbids rendering chain data as links.

### M6 — `minOut` and DEX order fields are under-specified (§8.1 #8, §8.3, §10.5)

**Unwrap.**
- `minOut` (TW2 R148, `UnwrapBelowMin`) must default to `previewUnwrap` at signing time exactly, never 0.
- If a rate change is pending and `executeAt < validUntil`, warn and shorten `validUntil` to before `executeAt`.

**DEX.** The `Order` struct (`dex.rs:18-22`) also carries:
- `taker` (venue requires 0 on the public book);
- the relayer fee `feeMode/fee/feeToken/feeRecipient` (venue: `feeMode ≤ 2`, ppm cap);
- amounts `< 2^128`;
- the market `min_base_amount`;
- `MAX_OPEN_PER_MAKER`.

None of these is in §8.3 or the review rows.

**Fix.**
- List them. The review shows the relayer fee separately from the market fee, and the default is `feeMode = 0`.
- R159a's `dex` block adds the relayer-fee policy and per-market minimums so the client can build a valid order.
- `config:from-deployments` must map the deployment's `order_book_dex` to `contracts.dex`. The deployment JSON's
  `"dex"` key is `MetaTxDex`, a different contract.

### M7 — The review must be decoded from the signed bytes, not produced next to them (R158, §5.1, §10.5)

**Problem.**
- "`Intent.display` is produced by the same code that produced the bytes" means an encoder bug renders correct
  numbers over wrong bytes.
- For extension wallets with digest-only envelopes, the wallet shows only a hex digest, so the app's review is the
  only check:
  - Aptos `scaas.metaop.v1:0x<digest>`;
  - Solana OCMS text;
  - TON `signData` cell;
  - Hedera ED25519 over a digest.
- Users trained to approve such strings will also approve them on a phishing origin.

**Fix.**
- `display = decode(signRequest)` per family (EIP-712 parse, BCS/cell/XDR decode), plus an assertion that the decoded
  fields equal `IntentParams`. This is D R267 `checkTerms(terms, shown)`; reuse it.
- Add "`decode(signRequest(buildIntent(p))) == p`" to the adapter contract suite.
- For digest-only envelopes the review shows "your wallet will display: `scaas.metaop.v1:0xABCD…1234`" so the user
  can match it, and the line "approve SCaaS messages only on <origin>".

### M8 — Strings from chain and network are attacker-chosen (§8.1 #2, #6, #21, #25; §10.6)

**Problem.**
- These strings come from attackers or untrusted peers:
  - token `name`/`symbol` (an open factory: anyone can deploy "USDC");
  - revert strings in `400 simulation: …`;
  - gossip peer fields (from untrusted peers);
  - audit before/after.
- React escapes HTML, but not bidi overrides (U+202E), zero-width characters, confusables or 10 kB names.
- "Deployed by factory X v N" reads as an endorsement, but `IOpenFactory` is permissionless.

**Fix.**
- One `untrustedText(s, max)`: NFKC, strip Cc/Cf (bidi controls included), cap at 32/64 characters, flag non-ASCII
  symbols. Use it for every chain or network string.
- The curated config label wins over the chain name.
- Badge non-curated tokens "unverified". Warn when a non-curated symbol equals a curated one on the same chain.
- Label provenance "created via the open factory (anyone can)" vs "curated by this deployment".
- Keep the current state of no markdown and no `dangerouslySetInnerHTML`, enforced by lint as stated.

### M9 — Supply chain and bundle budgets are not grounded (§3.2, §10.3, §14)

**Problem.**
- **Missing polyfill.** `@stellar/stellar-sdk`/`stellar-base` and `@ton/core` need a global `Buffer` under Vite.
  `buffer` is not on the allowlist, so it needs a ruling.
- **Transitive dependencies are not covered.** The allowlist names direct dependencies only.
  - cosmjs has historically pulled `elliptic` + `bn.js` + `libsodium-wrappers-sumo`.
  - stellar-sdk pulls axios, eventsource, urijs and bignumber.js.
  - `@ton/ton` pulls axios and zod.
- **Wrong TON client.** `@ton/ton`'s `TonClient` speaks toncenter **v2** jsonRPC, while the config example and the
  shim (`smartcontracts/ton/shim/server.ts`, `/api/v3/*`) are **v3**. `@ton/ton` is the wrong client and can be
  dropped: use `fetch` against v3 + `@ton/core`.
- **Duplicated crypto.** viem brings its own `@noble/*` 1.x while clientkeys pins 2.4.0, so the ≤ 90 kB EVM chunk
  carries two copies.
- **The budgets are guesses**, ratcheted only after A15.

**Fix.**
- A1 adds a spike: one minimal import per SDK, built into a throwaway chunk, gzip size recorded. budget.json starts
  from the measurements.
- CI checks transitive dependencies through a lockfile diff plus a package-count gate.
- Vet cosmjs at A9. If it still pulls libsodium/elliptic, build `MsgExecuteContract` and `TxRaw` over
  `cosmjs-types` + noble (clientkeys already has secp256k1).
- Decide on `buffer` now.

## Low

- **L1 — OIDC pinning (§9.4, R163).**
  - Problem: issuers come only from the node's `auth-modes`, so a misconfigured or hostile node can send the user to
    any IdP login page. Static `npm run csp` cannot include IdP origins because they are not in config (H6d).
  - Fix: add `nodes[].oidc: [{issuer, connectSrc: []}]`. Allowed issuers = `auth-modes ∩ config`; the same list feeds
    CSP generation. Store `issuer` with `state`, check RFC 9207 `iss` when the IdP sends it (oauth4webapi does), and
    keep the return hash route in the same `sessionStorage` entry.
  - PKCE, in-memory refresh and logout are otherwise sound.
- **L2 — Cut.**
