# `mldsa87` (0x0134): ML-DSA-87, FIPS 204 NIST level V, as a UA kind — design

**Status:** SPECIFIED, nothing built; the owner reviews this spec before any production code (owner 2026-11-04: "add ML-DSA-87
(FIPS 204, NIST level V) as a UA kind; spec and a measurement only"). The normative rules it extends are
[CTR-UA-06](../../contracts/accounts.md#CTR-UA-06), [CTR-UA-07](../../contracts/accounts.md#CTR-UA-07),
[CTR-UA-16](../../contracts/accounts.md#CTR-UA-16), [CTR-UA-23](../../contracts/accounts.md#CTR-UA-23) and
[CTR-PQZ-10](../../contracts/pq-zero-knowledge.md#CTR-PQZ-10) / [CTR-PQZ-12](../../contracts/pq-zero-knowledge.md#CTR-PQZ-12).
The measurement is [research/mldsa87-evm-gas.md](../../research/mldsa87-evm-gas.md); the probe is
`smartcontracts/evm/runs/2026-11-04-mldsa87-probe/`. Rows marked **follows** apply a stated rule and need no ruling; rows marked
**controller proposal** are the controller's and the owner may override them; §13 lists what only the owner can decide.

## 3. Measured (research)

> **Research note — background and rationale only, not normative; the current rules are in docs/ (see decisions.md).**

From [research/mldsa87-evm-gas.md](../../research/mldsa87-evm-gas.md) (forge, Foundry 1.8.5, Amsterdam, `isolate`; the built
`MlDsa` code with ML-DSA-87's parameters; all 30 NIST ACVP ML-DSA-87 sigVer cases of the pure and internal groups agree on both key
forms, and with `@noble/post-quantum` 0.7.1):

| | ML-DSA-65 (built) | **ML-DSA-87** |
|---|---|---|
| verify, FIPS 204 key | 18,897,368 | **31,914,727** — over 2^24 by itself |
| verify, expanded key | 5,771,287 | **8,651,358** |
| `verifyCached` / least working gas, cold | 5,815,139 / 5,902,586 | **8,643,140 / 8,763,152** |
| 66 % of 12,000,000 / of 10,500,000 | 7,920,000 / 6,930,000 | exceeded by 0.84 M / 1.83 M |
| expanded key | 36,928 B, 2 parts | **65,600 B**, 3 EIP-170 parts (21,504 / 21,504 / 22,592) |
| `cacheExpandedKey`, regular + state | 15.6 M + 57.1 M | **27.6 M + 101.2 M** (9.0–9.5 M regular a part) |

So one pure-Solidity verify **fits** `verifyBudget` (73 % of 12 M, 84 % of 10.5 M) and a 2^24 transaction with a registration's
other regular costs (≈ 9.0–9.2 M, estimate), and **does not pass** the 66 % rule on any chain.

## 4. Verifier (EVM) — SPECIFIED

`UAMldsaVerifier` (`src/ua/MlDsa.sol`) takes `0x0134` with three changes the probe made: `MlDsa.params87()` (k 8, l 7, τ 60,
β 120, γ1 2^19, γ2 (q − 1)/32, ω 75, c̃ 64 B, pk 2,592, sig 4,627), `_sameCt` for a 64-byte c̃, and the constructor's kind check and
probe length (`2,592 + 4,627 + 32`). `PqUA.tag(0x0134)` = `keccak256("scaas.ua.mldsa87.v1")`. The precompile path is unchanged
code: `pk ‖ sig ‖ pq_msg` to the candidate, a valid probe ⇒ the word 1, a flipped one ⇒ 0, else pure Solidity.

- **Candidates.** One per deployment, as today: `0x14` on a chain that ships EIP-8355 (Draft; EIP-8051 and EIP-7932 claim
  `0x12` / `0x13`, not `0x14`, and the probe guards against a different occupant either way); `0x…5caa0014` on the SCaaS testnet
  (and the same address on 22776 when it launches, as `0x…0012` / `0x…0013`, CTR-PQZ-10).
- **Without a precompile the kind is disabled** (M6): the deploy profile (`script/DeployBase.sol`) configures a PQ kind only where
  `_pqKindFits(cap, budget)` (cap ≤ 66 % of the budget) holds; `0x0134` gets the precompile cap where its verifier probed one and
  the Solidity cap ≈ 8.8 M elsewhere, which fails the test, so its verifier address is 0, `register` reverts `UAKindDisabled`, a copied
  record stays refused there, and nothing can receive on that chain under a kind it cannot spend (CTR-UA-23's reason).
- **Cache (M7).** `cacheExpandedKey(0x0134, …)` reverts `UAKeyCache(0x0134)`; `ekPtr` stays `address[2]` (no change to the pinned
  layout in `test/v2/layout/`). If the owner enables pure Solidity (Q1), the cache needs three EIP-170 parts — or two under the
  64 KiB code limit (≈ 12.0 M and ≈ 15.5 M regular, estimate) — and `ekPtr` grows, a layout change.
- **Cap.** Measured on the SCaaS testnet copy at build (T-GAS: accepting and rejecting inputs, through `requireAuthorized`), as the
  `mldsa65` precompile cap 200,000 was (P6g). Estimate until then: 0.2–0.3 M.

## 6. `msig` member limits at the budget — SPECIFIED

The bound is unchanged ([CTR-UA-38](../../contracts/accounts.md#CTR-UA-38), spec 2026-11-02-msig-nested §6):
`worst = Σ (cap + 45,000) over the c largest + 47,500 per inner msig + 2,500 (+ (held − 400 k) / 63 above 400 k) ≤ verifyBudget`.

| `mldsa87` path (cap) | One level | Two levels | Bound at the most signatures | Budget margin |
|---|---|---|---|---|
| precompile, cap 250,000 (**estimate**, measured at build) | 16 (the list) | **40** | 11,945,000 | 55,000 |
| the same, Hedera 10.5 M | 16 (the list) | **35** | 10,470,000 | 30,000 |
| pure Solidity, cap 8.8 M (disabled by M6; shown for Q1) | 1 | 1 | 8,980,833 (2L: 9,028,333) | 3,019,167 (Hedera 1,519,167) |
| hybrid `{mldsa87, p256}` t = 2, pure Solidity (Q1) | — | — | 9,425,833 | 2,574,167 |

With the measured cap the rows are recomputed and verified as msig-nested §6 did (`bound − 1` refused, `bound` accepted, one more
signature refused). Rows that verify must also **register**: an `msig` of 40 `mldsa87` signatures is ≈ 193 KB of `pop` calldata
(EIP-7976 floor ≈ 12.4 M regular); the "What registers" row is measured with it, never assumed.

## 7. SCaaS testnet precompile (Nethermind plugin) — SPECIFIED

`pqz-core/nethermind/Nethermind.Pqz/`: one class and one schedule key, as P6f R4 said.

- `MlDsa87Precompile` beside `MlDsa44Precompile` / `MlDsa65Precompile`: `MLDsaAlgorithm.MLDsa87`, `Pk87 = 2592`, `Sig87 = 4627`,
  `Base87 = 13_500` (EIP-8355), the same `MlDsa.Verify` (input `< pk + sig` ⇒ 32 zero bytes, a `CryptographicException` ⇒ 32 zero
  bytes), `PqzAddresses.MlDsa87 = 0x000000000000000000000000000000005caa0014`, a row in `PqzPrecompileProvider`.
- Schedule key `mldsa87Gas` (≥ `Base87`) in `PqzSchedule`. **Controller proposal:** optional per schedule — a schedule without it
  leaves `0x…0014` inactive (`DataGasCost` = `ulong.MaxValue`, the price of no schedule) — so the live chainspec's earlier
  schedules still parse; `MLDSA87` activates with the first schedule that carries the key. The contract probe (§4) detects it.
- `MlDsaKat` gains the ML-DSA-87 level (valid input, c̃ flip, hint order, hint padding, hint count over ω, `z` at γ1, t1 at its
  maximum, message flip: the eight rows of 44 / 65), so `ExpectedHash` changes; `SpecTests` drops "unknown key `mldsa87Gas`".
- `mldsa87Gas` value: from the `Calibrate` tool, a timing run that waits for the owner's word (no calibration without asking);
  until then a provisional row. Estimate by the 65 ratio (68,000 at EIP-8355's 9,000): ≈ 102,000.
- A new image (`build-image.sh`, built locally, never pushed) and a chainspec schedule; the roll-out of the live testnet stack is the
  owner's step.

## 13. Open points for the owner

1. **Q1 — pure Solidity.** The 66 % rule disables `mldsa87` wherever no ML-DSA-87 precompile exists (8.76 M measured vs 7.92 M;
   Hedera 6.93 M). This spec follows it: today `mldsa87` is registrable only on the SCaaS testnet (and on any chain where EIP-8355's
   `0x14` is probed). Keep it so? (Enabling it elsewhere would need the rule changed, the three-part cache and an `ekPtr` layout change.)
2. **Q2 — PQZ / KEM holder.** CTR-UA-16 and CTR-PQZ-12 name the holders (`mldsa44`, `mldsa65`, `fndsa512`, a PQ-eligible `msig`);
   `mldsa87` is not named, so as written it is no holder. The reason given for leaving `slhdsa128s` out (a 7,856 B signature and
   ≈ 1.4 M gas on every spend) does not describe `mldsa87` on a precompile (4,627 B, ≈ 0.25 M). Is a level-V signer a holder?
3. **Q3 — PQ weight in an `msig`.** CTR-PQZ-12 counts kinds `0x0130`–`0x0133` as PQ weight; `0x0134` falls outside the range, so
   as written an `mldsa87` member weighs as classical in the eligibility test (code: `UAStore.isPq`; the clients' `msig`
   eligibility ranges). Does `mldsa87` count as PQ weight?
4. **Q4 — the testnet precompile.** `0x…5caa0014`, `mldsa87Gas` optional per schedule (§7), and the calibration run that fixes
   its value: when may it run?
5. **Q5 — order.** EVM first (registry + testnet precompile), then each family in its round; Soroban can use CAP-0087 directly.
