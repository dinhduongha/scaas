## 4. Verifier (EVM) — SPECIFIED

One verifier contract for both Falcon sizes, as `UAMldsaVerifier` serves three ML-DSA levels: `UAFndsaVerifier` gains a
constructor kind (`0x0132` or `0x0135`) and the library takes `logn` (9 or 10) with its four constants: pk length 897 / 1,793
and header `0x09` / `0x0A`, signature length 666 / 1,280 and header `0x39` / `0x3A`, bound 34,034,726 / 70,265,242, n 512 /
1,024. **One zeta table serves both:** the first 512 entries of the Falcon-1024 table (`1945^brv10(k) mod q`) are exactly
today's Falcon-512 table (checked byte for byte), so the built 1,024-byte constant becomes one 2,048-byte constant.
Everything else is the built code: the SHAKE256 hash-to-point, `PqNtt`, the reference `comp_decode` (`|v| ≤ 2047`, no "−0",
zero tail) and the norm loop. `PqUA.tag(0x0135)` = `keccak256("scaas.ua.fndsa1024.v1")`. `UAFndsaVerifier(0x0132)` keeps its
behaviour (a redeploy of an unchanged kind is a catalogue entry, not an upgrade; the Falcon-512 rows of `FnDsa.t.sol` stay).

- **Precompile.** None to probe: EIP-8052 (Draft) defines Falcon-512 only and no address. If an EIP later defines a Falcon-1024
  precompile in this encoding, the verifier probes it as `UAMldsaVerifier` probes EIP-8355 (a valid probe ⇒ 1, a flipped one
  ⇒ 0, else pure Solidity); that is a new verifier deployment, not this one.
- **Cap.** T-GAS at build: accepting and rejecting inputs through `requireAuthorized`, the worst hash-to-point (most squeezes)
  and the longest decodable s2; until then F6's 5,250,000. `requireAuthorized` ≈ 4.80 M (estimate: `fndsa512`'s
  `requireAuthorized` 2,343,443 is its verify + 76,544).
- **Signature length.** The padded form is fixed at 1,280 B; a signer whose compressed s2 exceeds 1,239 B signs again
  (`falcon1024padded` does). One NIST KAT row of 100 (count 82, 1,240 B) has no padded form: not a verifier case.

At the proposed cap 5,250,000 the hold term is 76,984:

## 7. SCaaS testnet precompile — not proposed (owner Q5)

Pure Solidity passes the 66 % rule, so the kind does not need a precompile anywhere. A native one in
`pqz-core/nethermind/Nethermind.Pqz/` would be one class and one schedule key (P6f R4), but unlike ML-DSA (.NET
`System.Security.Cryptography.MLDsa`) .NET has no Falcon: the plugin would need a new dependency (a managed Falcon, or the
reference C through `Native.cs`), its own KAT class, an address in the plugin's 32-bit form and a gas value from a calibration
run the owner allows. No EIP fixes a Falcon-1024 input layout to copy (EIP-8052 is Falcon-512, split in hash-to-point and core).
The controller proposes not to build it; if the owner wants it, it is specified then.

## 13. FIPS 206 risk — SPECIFIED

`fndsa1024` v1 is **Falcon round-3 specification v1.2**, pinned by the NIST round-3 KATs and the noble vectors. **No FIPS 206
draft is published** (read 2026-11-04: the NIST CSRC FIPS list, <https://csrc.nist.gov/publications/fips>, shows FIPS 203 /
204 / 205 and no FIPS 206; the drafts open for comment list no FIPS). NIST's last public statement is Ray Perlner, "FIPS 206
Status Update", Sixth PQC Standardization Conference, 2025-09-25
(<https://csrc.nist.gov/presentations/2025/fips-206-fn-dsa-falcon>): an Initial Public Draft "soon … basically written, awaiting
approval", with **provisional** changes that each change what a verifier accepts or how its inputs are encoded:

| Provisional FIPS 206 change (slides) | Effect on a round-3 `fndsa1024` |
|---|---|
| public key in NTT form `ĥ` | a different key encoding (and a different UA id: the id hashes the key data) |
| little-endian encodings | different key / signature bytes |
| pure / pre-hash versions, the BUFF transform (the message hash binds the public key) | a different hash-to-point input: round-3 signatures fail under FN-DSA and the reverse |
| verification bounds the infinity norm as well as the L2 norm | FN-DSA refuses some signatures round 3 accepts |
| only randomized signing; 40-byte pseudorandom seeds | signer side; our vectors' fixed randomness is a test device only |

**A final FIPS 206 that differs is a new kind version** (a new id and tag, e.g. an FN-DSA-1024 kind beside `fndsa1024`), never a
silent change, as accounts.md CTR-UA-23 rules for `fndsa512`; the v1 kind stays verifiable as registered (nothing deployed is
upgraded). Building `fndsa1024` now means a second Falcon kind that FIPS 206 is expected to supersede (owner Q1).

## 14. Owner answers (2026-11-04)

The questions as they were asked stay in git history (`60387404`); the answers, in full:

1. **Q1 — build now: yes.** `fndsa1024` (round-3 specification v1.2) is built on the EVM now, as specified, accepting that a
   final FIPS 206 that differs from round 3 is a new kind version later (§13: a new id and tag beside `fndsa1024`, never a
   silent change; the v1 kind stays verifiable as registered).
2. **Q2 — PQZ / KEM holder: yes.** `fndsa1024` is a direct holder of a PQZ key and a KEM record: added to the holder list of
   CTR-UA-16 and CTR-PQZ-12 (`UARegistryLib._holder`, and `PqzCore._creditKey`'s PQZH single-key holder list).
3. **Q3 — PQ weight in an `msig`: yes.** `0x0135` counts as PQ weight: `UAStore.isPq` covers `0x0130`–`0x0135`. The slot map is
   separate: `0x0135` → a new slot 20 (`_CFG20`), mapped before the `isPq` check, because the PQ formula `kind − 0x0130 + 14`
   would give 19, `secp256k1`'s slot; "not in the table" becomes 21.
4. **Q4 — NTT-key cache: no.** The key is used as registered (`keyPtr`); no cache, no second stored form.
5. **Q5 — SCaaS testnet precompile: no.** Pure Solidity on every EVM chain, the SCaaS testnet included: it passes CTR-UA-23's
   66 % rule (4.93 M at the largest KAT; 41 % of 12 M, 47 % of Hedera's 10.5 M). The cap is 5,250,000 until T-GAS replaces it
   (F6, **provisional**). No Nethermind change.
