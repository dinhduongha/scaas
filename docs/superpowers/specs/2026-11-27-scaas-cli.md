## 1. Scope and place

**BUILT.** `scaas` is a thin client of `scaas-sdk` ([CLI-SDK-17](../../clients/scaas-cli.md#CLI-SDK-17)): one command per SDK
call, no logic of its own, and the reference client of the SDK's end-to-end tests (the gate step `cli-e2e`, §7). It never
calls `scaas-tui`, and `scaas-tui` never calls it: the two share call and action names only
([CLI-TUI-01](../../clients/scaas-tui.md#CLI-TUI-01)). The CLI runs one call per command (or one per line in a session, §2.3);
the TUI is the interactive front-end that follows events.

What it links (`clients/scaas-cli/Cargo.toml`, as built):

| Crate | Features |
|---|---|
| `scaas-sdk` (no default features) | `vault`, `account`, `wallet`, `evm`, `file-store`, `mlock`, `zether`, `pqz`, `pqz-set-n2304-kmax4096`, `dex`, `admin`, `classical-roots`, `app-core`, `pqchat-records`, `native-networks`, `near`, `algorand`, `cosmos`, `aptos`, `solana`, `soroban`, `sui`, `ton` |
| `scaas-ua` (`ua-rs`, no default features) | `wallet` and every family: `fam-evm`, `fam-hedera`, `fam-near`, `fam-algorand`, `fam-cosmos`, `fam-aptos`, `fam-solana`, `fam-soroban`, `fam-sui`, `fam-ton`, `fam-dot`, `fam-btc`, `fam-arweave` |
| `scaas-rpc` (no default features) | — |
| the CLI's own feature | `dev-profiles` (forwards `scaas-sdk/dev-profiles`): `--profiles <file>`, §5.1 |

What it never links: `raw-native` and `opaque-calls` (no input that signs undecoded bytes, as the TUI's
[CLI-TUI-17](../../clients/scaas-tui.md#CLI-TUI-17)), `vectors` (the SDK's test feature, refused by
`scripts/check_test_features.py`), and `arweave` (an Arweave upload is public and permanent; [CLI-SDK-21](../../clients/scaas-sdk.md#CLI-SDK-21)).
The SDK calls those features add are listed as excluded with their reason (§2.1). One PQZ set is compiled in,
`n2304-kmax4096`. The CLI configures no `Authenticator` (`SdkConfig.authenticator` is `None`), so passkey and platform unlock (`--by passkey`,
`--by platform`) have nothing to answer them.

**Why a thin client.** The SDK holds every rule a signing app must keep (review, quote, secrets, state); a CLI with logic of
its own would be a second implementation of them. The CLI is also how the SDK's e2e runs as a user would: a binary, a data
directory and a terminal.

## 2. Command model

### 2.1 One command per SDK call

**BUILT** (T22 (a), CLI-SDK-17). `scaas [options] <group> <call> [--flag value…]`: the group is the SDK module or type
(`vault`, `account`, `wallet`, `confidential`, `dex`, `admin`, `op`, `app-core`, `sdk`, and the object types `prepared`,
`registry-write`, `prepared-order`, `seed-backup`, `keystore`, `ua-line`, `signed-op-blob`, `registration-blob`,
`subscription`, `subject-key`, `msig-structure`, `op-state`, `gas-table`); the call is the SDK call's own name with `-` for
`_`. The table in `src/calls.rs` (the `calls!` macro) is the one list: each row names the command, the SDK call it runs, its
flags, its secrets and its confirm class, and the same rows produce the dispatch, `scaas commands` and the flag list, so they
cannot drift apart. As at `66a39524c`: **335 commands** in 23 groups (admin 68, app-core 65, account 37, wallet 35,
confidential 28, vault 25, op 16, dex 13, sdk 8, registry-write 8, prepared 7, keystore 7, prepared-order 4, seed-backup 3,
and nine groups of one or two), and 31 SDK calls excluded with a reason (`calls::EXCLUDED`: the module accessors, `Sdk::open`,
`Sdk::spawn`, `Sdk::authenticator`, the store constructors, `AppCore::new`, `SdkError::code`, the three `*Prepared::sign` calls
signed inside their `prepare-*` commands after the confirm, the features the CLI does not link, and three pure transforms).
`tests/cli.rs` `one_command_per_sdk_call_both_ways` holds the table equal to the SDK's public calls in both directions.

Flags: a request struct's fields, flattened (`(r: Type)` rows), or one flag per parameter (`{a: T, …}` rows); `--a.b x` for a
nested field; a repeated flag is a list; `{…}` and `[…]` values are JSON; a value is read as the SDK field's type asks (a
number, a bool, text, `0x` hex for bytes); a flag written with `-` reaches the field with `_`. Unknown flags are refused
(`UnknownFlag` before the command, the SDK types' `deny_unknown_fields` inside it, `Argument`). The SDK's public data types
derive `serde` with `deny_unknown_fields` for this (T22 (b)); a type holding a secret, an SDK object or a platform interface
has no `Deserialize`, so it cannot come from a flag.

Options before the command: `--data-dir`, `--profiles` (only in a `dev-profiles` build), `--overlay`, `--unlock <seed>`
(repeatable; with `--passphrase-fd`), `--passphrase-fd`, `--app <file>` (the `AppDesc` of the `app-core` group), `--path`
(a `SubmitPath` by name or as JSON; default `Auto` with no payer), `--as <name>` (a session), `--json`, `--yes`.

### 2.2 Confirm classes

**BUILT** (T22 (e), 2026-11-21 Change (i), (ii)). Each row declares its class, listed by `scaas commands` as `confirm`:

- **`op`** (130 commands): the call returns an operation object (a prepared operation, registry writes, a DEX order, a native
  send quote). The body's type must be one (`IntoOp`), so it cannot submit; one command then runs it to its end in `finish`:
  quote, print the review and the quote, ask, submit, wait up to 30 s for the send's `OpState` event.
- **`sign`** (39 commands): the call signs with a held key or submits (`op submit`, `op resend`, `account
  submit-registry-write`, `wallet submit-native-send`, `dex place`, `dex cancel-all`, `dex sign-order`, `op member-sign`,
  `op hand-off`, the Soroban submits and hand-off, the BLS parts and registration, the auditor consents, the rescue vault, app
  and PqChat records and messages, `app-core prepare-app-call`, `vault remove`); its body
  prints what it signs and asks before the SDK call.
- **none** (166 commands): neither signs nor submits (reads, local rows, a new seed, an unlock, pure transforms).

The answer is `y` or `yes`; anything else is `NotConfirmed` and nothing is signed or sent. `--yes` answers for a script. In a
session the answer is read from the terminal (`/dev/tty`), since stdin carries the commands; with no terminal the confirm
refuses (`NoTerminal`).

### 2.3 Sessions

**BUILT** (T22 (c), Change (iii)). SDK objects live in one process. A single command runs an `op` to its end, so a prepared
operation never has to leave the process. `scaas [options] session` reads one command per line from stdin, each a JSON array
of words; `["--as", "p", "wallet", "prepare-pay", …]` names what the call returns, and later lines pass it by name
(`["op", "submit", "--prepared", "p", "--quote", "q"]`). In a session an `op` command does not submit: it keeps the object and
prints `{"handle": name, …}`. Kept objects: a prepared operation, registry writes (also each as `<name>.<i>`), an order, a
native quote, a quote, an app key, a subscription, a `UaLine`, a seed backup. Outside a session such an object prints its
shown fields and the note that it lives in one process.

### 2.4 Waiting for the send

**BUILT** (T22 (c); [CLI-SDK-18](../../clients/scaas-sdk.md#CLI-SDK-18)). After `submit` the command waits for the SDK's
`OpState` event of its operation, at most 30 s, and prints `{"op", "state"}`; without it, the state is "not reported yet" and
`op state` follows it, `op resume` sends a row not yet sent. An exit never cuts a send short; an operation ends only on a
chain fact (CLI-SDK-18).

## 3. I/O contract

**BUILT** (T22 (h); [CLI-CMD-01](../../clients/scaas-cli.md#CLI-CMD-01)).

- **Output.** One JSON object per line on stdout with `--json`; otherwise named rows `a.b: value`, one per leaf, anything
  outside printable ASCII drawn as `\u{…}` (`table_escapes_what_a_terminal_acts_on`). A result is an SDK type's `serde` form
  or a named object (`{"ok": true}`, `{"in_list": …}`, `{"op": …, "state": …}`); the confirm prints its object (`review`,
  `quote`, `prepared`, `chain`, `entry`) the same way before the question. At most 1 MiB per output, else `OutputTooLarge`
  and nothing printed (`output_bounded`). `json_output_has_named_fields` holds the named fields.
- **Errors** ([CLI-CMD-01](../../clients/scaas-cli.md#CLI-CMD-01)). On stderr: `error: <Code> <detail>`, or with `--json`
  `{"error": "<Code>", "detail": "…"}`. The code is the SDK's stable code (`SdkError::code`) or the CLI's own (`Argument`,
  `UnknownCommand`, `UnknownFlag`, `NotConfirmed`, `NoTerminal`, `SecretUnreadable`, `OutputTooLarge`, `ProfilesPinned`,
  `ProfilesRefused`, `DataDirMissing`, `DataDirUnusable`, `AppMissing`, `Internal`). The CLI's detail names a flag, a file or
  a count, at most 64 characters, escaped; an SDK refusal prints no detail.
- **Exit codes.** 0 success; 1 a refusal; 2 an unknown command or flag; 70 when the runtime cannot start.
- **Stability.** Nothing versions the JSON today: its shape is the SDK's `serde` form, which moves with the SDK
  (`sdk api-version` reports the SDK's API version). Proposed in §8 Q1.

## 4. Secrets

**BUILT** (T22 (d), CLI-SDK-17; tests `no_secret_flag_exists`, `secret_never_from_environment`, `generate_reveals_once`,
`secret_line_bounded`).

- A secret (a passphrase, words, a key, a signature, backup answers) comes only from `--<name>-fd N` (read from `/dev/fd/N`;
  `0` is stdin in a single command; two secrets on one descriptor are read in turn) or from the terminal without echo
  (`rpassword`); never from argv, never from the environment. No command has a flag that takes a secret's value: each row
  names its secrets (`scaas commands` lists them as `secret_fds`), and the test holds that no other flag is one.
- One line, at most 4,096 bytes, UTF-8; a key or a signature is `0x` + hex on its line. The line is zeroized after use.
- `--unlock <seed>` unlocks with the passphrase from `--passphrase-fd` (or the terminal) before the command.
- A new seed's words are shown once, after the typed word `reveal`; `--yes` never answers it; no answer (no terminal in a
  session) keeps them hidden. In a session the backup is kept by name for `seed-backup challenge` / `verify` / `reveal`;
  in one command it is closed.
- No secret is printed: `vault signature-from-compact` reports only that the signature is valid; an app key prints as a
  handle that is never readable.

## 5. Profiles, overlay and data directory

### 5.1 Pinned chain profiles

**BUILT** (CLI-SDK-17's Change of 2026-11-17, R17; T22 (f); test `profiles_pinned`). A release build takes the profiles
compiled into it (`clients/scaas-cli/profiles/release.json`, `include_str!`) and no other; `--profiles` is `ProfilesPinned`.
As at `66a39524c` that file holds no profile (`{"profiles": []}`): a release build reaches no chain until a release ships its
profiles. A `dev-profiles` build may take `--profiles <file>` (at most 64 KiB) and prints on every run a banner naming the
file's SHA-256, or that it runs the release profiles. A profile without a stated finality (the tag or a depth) is
`ProfilesRefused` (decisions CLI-SDK-32). The digest-pinned file shipped beside the binary (the rule's second form) is not
built.

### 5.2 The overlay

**BUILT** (T22 (g); test `overlay_lowers_caps_and_adds_credentials_only`, `credential_file_readable_by_others_refused`).
One JSON file, `--overlay` or else `$XDG_CONFIG_HOME/scaas/overlay.json` (`~/.config/scaas/overlay.json`) when it exists,
unknown fields refused, at most 64 KiB. It holds only lower `limits` (a cap may only go down) and `credentials` per endpoint
label: a file path (refused when group- or world-readable) or an environment variable's name, never a value. It has no field
for a `chain_uid`, a contract or an endpoint list.

### 5.3 The data directory

**BUILT** (CLI-SDK-17; test `cli_and_sdk_share_a_directory`). `--data-dir`, else `$XDG_DATA_HOME/scaas`
(`~/.local/share/scaas`); the SDK's `FileStore` over it, under the keystore's lock, so the CLI, `scaas-tui` and the app share
one directory and never write it at the same time. No directory found is `DataDirMissing`; one the store cannot use is
`DataDirUnusable`.

## 6. Planned

- **User profiles** (PLANNED; [CLI-UPR-01](../../clients/scaas-sdk.md#CLI-UPR-01) to CLI-UPR-28, spec
  [2026-11-27-user-profiles.md](2026-11-27-user-profiles.md)). Today the data directory is one profile. When the SDK's
  `UserProfiles` exists the CLI gains its calls as commands like any other (one per call, CLI-SDK-17): a `profile` group
  with list, create, open, switch, export, import and lock, the passphrases by descriptor or terminal (§4), export and import
  to a file path named by flag, and the typed confirm of an export or a removal through the confirm of §2.2 (a removal is
  `sign`-class as `vault remove`). `--data-dir` then names the profiles' root. The table test (§2.1) makes this automatic: a
  new SDK call without a command fails it.
- **`SignReview`** (PLANNED, after the pre-freeze tag; [CLI-SDK-35](../../decisions.md#CLI-SDK-35)). The confirm prints the
  SDK's review rows (`ReviewField`) as they are today. When the SDK emits `SignReview`, the confirm prints it instead: the
  same `--json` object (its typed rows with source and visibility) and, as a table, one row per field with its source; no
  rendering logic in the CLI beyond the escaping of §3.
- **Sign after confirm** (BUILT for the CLI's own signing; [CLI-SDK-36](../../decisions.md#CLI-SDK-36)). Every `sign` row asks
  before its SDK call, and the app and PqChat records are signed inside their `prepare-*` commands after the confirm on their
  review (T26 A-5; `AppPrepared::sign`, `PqChatPrepared::sign`, `PqCardPrepared::sign` have no command of their own). Gap: the
  confirm shows the SDK's review rows and, for records, no quote yet; CLI-SDK-36's quote from the record's sizes arrives with
  the app cores' change.
- **App cores** (SPECIFIED: what exists). The `app-core` group (65 commands) is the SDK's `AppCore` over `--app <file>`:
  seal, open, keys, records, PqChat records and envelopes. `pqvault-core` and `pqchat-core` themselves are not linked: they
  are app cores above the SDK (CLI-SDK-19), and the CLI is a client of the SDK only. Proposed in §8 Q2.

## 8. Open questions for the owner

**Q1 — JSON stability.** The JSON is the SDK's `serde` form and moves with it. Recommendation: the CLI's `--json` is the SDK's
API: a change that renames or removes a field, or changes its type, moves `Sdk::api_version()`'s major and is listed in the
commit; adding a field does not. A script reads `sdk api-version` first. No separate CLI schema.

**Q2 — App-core commands.** The CLI exposes `AppCore`'s 65 calls; PqVault and PqChat flows (a vault's items, a chat session)
live in their app cores, which the CLI does not link. Recommendation: keep the CLI at the SDK (its role, CLI-SDK-17); the
PqVault and PqChat flows go to `scaas-tui`, which links both cores ([scaas-tui.md](../../clients/scaas-tui.md)); no `pqvault` / `pqchat` groups in the
CLI.

**Q3 — Offline prepare → sign → submit.** Objects live in one process; the only cross-process form is the hand-off blob
(`op hand-off`, `op import-signed`). Recommendation: no new offline format; an air-gapped signer uses the hand-off blob, which
the payee imports, quotes and submits.

**Q4 — Shell completion.** Recommendation: a `scaas completions <shell>` command generated from the same `calls!` table
(bash, zsh, fish), with a test that every command appears; it carries no logic and no secret.

**Q5 — A release's profiles.** The release profile file is empty. Recommendation: the release ships the profiles of the
chains in [chain-support.md](../../networks/chain-support.md) marked for release, compiled in (the rule's first form); the
digest-pinned file beside the binary stays unbuilt until a packager asks for it.
