## 5. isValidPoint aliases (review I4)
None on either curve. BN254 (`G1Bn254.isValid`): exactly 64 bytes, through the EIP-196 ECADD precompile with O, which refuses
a coordinate >= p, so each point has one encoding (x, y). BLS12-381 (`G1Bls12381.isValid`): exactly 128 bytes, through the
EIP-2537 G1MSM precompile, which refuses a field element whose top 16 bytes are not 0 or whose value is >= p and checks the
subgroup. `AuditorSame()` compares the bytes (keccak256), which is the canonical comparison.

## 6. A proven-key view in the registry (plan A4 step 1)
Yes: `pqzKeyOf(ua)` and `pqzKeyAt(ua, v)` (the registry key, `PRECOMPILE`) and `pqzScopedKeyOf(ua, scope)` /
`pqzScopedKeyAt(ua, scope, v)` (the shared key, scope 0, and the token's key, scope = the token) return `bool proven`: true
once `storePqzPop` / `storePqzScopedPop` stored the R_REG proof and the 0x0142 verifier checked it (UA8-D9, K3-3). There is no
view named `checkedPqzPop`. A4 requires `proven` of the new auditor's current key of the token's class and scope.
Consequence to note (reported to the coordinator): on a registry without a 0x0142 verifier, `proven` is never true, so an
`OFFCHAIN` token's setter would refuse every new auditor there.
