    - they bind the kind's latest env and check each library's `extcodehash`;

  - `createDex(version, bytes initArgs, salt)`.
  - The index and `TokenCreated` read the token's `underlyings()`, `features()`, `lockedFeatures()` and `owner()`
    after `initialize`.
  - Removed: `Canonical`, `zetherVerifiers`, `pqzVerifier`, `registerImplementation`, `registerDexImplementation`,
    `zetherEnabled` / `pqzEnabled`, and the Zether / PQZ factory errors.

## Owner questions (answered 2026-10-20, see "Results")

- **Notice-period defaults:** 10 minutes on 7622, 3 days on 22776. Confirm or give values.
- **Generic initialize:** it takes `(creator, version, initArgs)`, not `(Env, initArgs)`. The Env is already the
  release's (constructor immutables), so passing it again would add nothing. Confirm.
- **Env binding:** `deployImplementation(kind, version, initcode, implArgs)` binds the kind's latest published env, with
  no env-version parameter, to keep the owner's signature. Confirm, or ask for an explicit env version.
- **Library pinning:** `Env.libs` is the registrar's list of the libraries the release links, each pinned by code hash.
  The factory does not parse the init code to check that list against the bytecode's link references.
- **Removed factory-level gates:** the dev-chain and verifier gates that were in the factory (`setZetherEnabled` on dev
  chains only, `_checkZether`, `_checkPqz`) now live only in the implementations' `initialize` (ZetherSafety, the
  verifier's `isSupportedOnThisChain`, `PqzSafety.requirePqz`), as the owner directed.

### Controller proposals made in Z2 (owner may override)

2. Kind gate defaults: plain kinds enabled, confidential kinds disabled at construction; `setKindEnabled` runs no chain
   check (the token's `initialize` does), so on a non-dev chain a Zether kind can be enabled but every creation reverts.
3. Confidential kinds refuse a Hedera env (`BadInit`) in their constructors.
4. The DEX env domain is `type(uint8).max` (255) in `EnvPublished` / `EnvUnknown`.
5. `latestEnvVersion` / `latestDexEnvVersion` kept as views (no factory logic uses them now; clients and tooling may).
6. DeployBase publishes one Zether env per curve for both Zether kinds, listing five libraries (`UnderlyingLib` too,
   which `NoUnderlyingZetherToken` does not link): an extra pin is harmless and keeps one env per curve.
